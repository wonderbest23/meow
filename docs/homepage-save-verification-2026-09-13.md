# 홈페이지 데이터 연결과 저장 보완 결과

최신 후속: 아래에 남겨 두었던 최초 프로젝트 생성 경합을 실제 로컬 DB에서 재현하고 트랜잭션으로 수정했다. 인증된 저장/공개/복원/문의 16개 검사와 PC/모바일 브라우저 결과는 [홈페이지 전체 연결 검증](./homepage-lifecycle-verification-2026-09-13.md)을 참고한다. 아래의 최초 검증 당시 기록은 그대로 유지한다.

기준일: 2026-09-13. `product-readiness-2026-09-13.md`의 첫 번째 후속 작업 기록이다.
같은 날 진행한 다음 단계인 실제 템플릿의 사업 문구 반영과 모바일 편집 검증은 [사업 내용 반영 검증](./homepage-business-content-2026-09-13.md)에 기록했다. 아래의 미완료 항목은 이 문서 작성 당시 상태다.
이번 범위는 대화 사업안에서 홈페이지 초안으로 가는 데이터 변환, 실제 에디터 저장, 실패 복구, 동시 탭 저장 방어다.
운영 배포, 실제 결제, 유료 AI, 운영 Supabase 쓰기, 홈페이지 공개는 실행하지 않았다.

## 완료한 변경

- 홈페이지 준비 검사와 초안 변환이 같은 선택 사업의 코치 데이터를 읽는다. 현재 코치의 상품, 고객, 가격이 기존 설문보다 우선한다.
- 전역 사업 정보로 다른 사업의 이름이나 업종을 섞지 않도록 생성 라우트를 변경했다. 기존 설문형 데이터도 계속 지원한다.
- 제안 가격에는 제안임을 표시하며 운영 중 사업의 문제, 매출, 비용 등 내부 정보를 공개용 설명으로 가져오지 않도록 범위를 제한했다.
- 이미 만든 홈페이지가 있으면 새 사업안으로 수동 편집 내용을 덮지 않는다. 준비 항목이 나중에 비어도 기존 홈페이지를 우선 불러온다.
- 편집기 저장이 실제 서버 저장 응답까지 기다린다. 성공한 경우에만 편집기를 닫고, 실패하면 수정 내용과 오류 안내를 유지한다.
- 저장 중 중복 입력을 막고 네트워크 실패, 시간 초과, 응답 확인 실패를 처리한다. 계정 변경 시 진행 요청을 중단하고 기존 계정의 화면을 비운다.
- 마지막으로 읽은 `updatedAt`을 저장 요청에 포함한다. 이전 버전으로 다른 내용을 덮으려 하면 HTTP 409로 거절한다.
- 서버에서 저장은 됐지만 응답을 잃은 경우, 같은 내용을 재시도하면 기존 저장 결과를 돌려준다. 변경된 다른 내용을 강제로 덮어쓰지는 않는다.
- 짧은 상호가 초안 검증에서 거절되던 조건을 수정했다. 기존 최소 5글자 제목 조건 때문에 `새벽커피`도 저장할 수 없었다.
- 기본 템플릿 편집기와 블록형 편집기 모두 비동기 저장 계약을 사용한다. 블록형 편집기의 저장/오류 상태는 헤더 재렌더링과 분리했다.

## 저장 API 변경

`PUT /api/projects/:projectId/landing`은 이제 다음 형태를 요구한다.

```json
{
  "draft": { "...": "홈페이지 초안" },
  "expectedUpdatedAt": "마지막 서버 응답의 updatedAt"
}
```

최초 생성에만 `expectedUpdatedAt: null`을 사용한다. 기준 필드가 없는 이전 클라이언트에는 428과 새로고침 안내를 반환한다.
현재 알려진 UI 저장 호출은 모두 새 형식으로 변경했다. 배포 시 클라이언트와 API를 함께 배포하고 오래 열어 둔 탭도 확인해야 한다.
Supabase 경로는 `project_id`와 `updated_at` 조건을 포함하는 단일 UPDATE를 사용한다. 기존 `updated_at` 트리거를 전제로 하며 새 DB 마이그레이션은 적용하지 않았다.

## 남은 작업과 다음 순서

1. **사업 데이터와 템플릿의 실제 표시 문구 연결**
   - 현재 `createLandingPageData`의 기본 kit는 `texts: {}`를 만들고 사업명은 `root.props.title`에만 넣는다. kit 렌더러는 이 제목을 자동으로 문구 슬롯에 넣지 않는다.
   - 따라서 이번에 수정한 초안 메타데이터와 실제 템플릿 화면의 사업별 문구는 아직 별도의 문제다. 이를 해결하기 전 홈페이지 자동 생성이 완성됐다고 안내하면 안 된다.
   - 사업명, 상품, 고객, 문의 등 확인된 정보를 템플릿 슬롯에 매핑하고 예시 실적/후기/숫자는 제거하거나 분명한 예시로 분리한다. 기존 수동 수정은 보존한다.
2. **홈페이지 연결의 남은 경계 검증**
   - 같은 사업의 첫 생성 요청이 동시에 들어오면 `ensureProjectForPlan`의 조회 후 생성 사이에서 서로 다른 프로젝트가 생길 가능성이 남는다. 현재 생성 보호는 같은 프로젝트 안의 홈페이지에 적용된다. 프로젝트 연결의 DB 유일성/원자성 보완이 별도로 필요하다.
   - 실제 Supabase에서 조건부 저장과 트리거, 인증된 전체 페이지의 계정 전환, 구버전 탭, 저장 중 권한 변경을 검증한다.
   - 충돌 시 내용은 편집기 메모리에 유지된다. 새로고침 후 미저장 수정본 복구나 자동 병합은 아직 제공하지 않는다. 최신 내용 비교 후 다시 적용하는 UX도 보완 대상이다.
   - 편집기 열림 자체에도 보수적으로 이탈 경고를 표시한다. 입력 여부를 더 정밀하게 구분하고 브라우저 뒤로 가기까지 검증할 필요가 있다.
3. **세 고객 여정 확인**
   - 아이디어 없음, 기존 사업 운영 중, 플랫폼에서 시작한 사업의 재방문 개선을 같은 사업 ID와 이전 자료를 유지하며 검증한다.
4. **지속 운영 리포트의 데이터/화면 연결**
   - 기간별 실적, 전후 비교, 개선안 선택, 과거 계획서 보존, 새 리포트 이력을 별도 작업으로 구현한다. 이번 저장 보완으로 이 기능이 완료된 것은 아니다.
5. **스테이징에서 실제 생성과 공개 검증**
   - Google 로그인, 테스트 결제, PDF/Word/PPT 실제 파일, 이미지 업로드, 홈페이지 공개/재공개/복구를 검증한 뒤 출시 가능 범위를 확정한다.

이번에는 커밋, 푸시, 배포를 실행하지 않았다. 이전 작업의 수정 파일도 되돌리지 않았다.
