# 사업 재방문과 운영 개선 연결 검증

기준일: 2026-09-13. [홈페이지 사업 내용 반영](./homepage-business-content-2026-09-13.md) 다음 단계로 진행했다.
대상은 신규 사업, 이미 운영 중인 사업, 이 서비스에서 시작한 사업의 재방문이다.
운영 DB, 실제 유료 AI, Google 로그인, PG, 파일 다운로드, 홈페이지 공개, 커밋과 배포는 실행하지 않았다.

## 이번에 보완한 것

### 운영 단계 유지

- 같은 사업이 운영 중이면 모델의 후속 응답이 `startup` 또는 `exploring`으로 잘못 분류해도 운영 단계는 유지한다.
- `사업을 운영 중이에요`라는 진입 선택도 명시적인 운영 의도로 처리한다. 그 외 자연어 단계 판단은 기존 모델 경로를 사용한다.
- 사업 설명의 단계, 문서 개정 번호, 두 번째 사업안 설계 호출의 맥락에도 보정된 단계를 적용한다.
- 운영 중인 사업의 설계 후 추천 질문을 현재 문제와 다음 개선 실험으로 바꿨다.
- 별개 새 사업은 새 대화/새 사업 ID로 시작한다. 같은 ID의 운영 사업을 모델 판단만으로 창업 전 사업으로 바꾸지 않는다.

### 기존 기록을 남기는 운영 개선 전환

- 운영 중인 사업의 관리 메뉴를 `운영 개선하기`로 표시한다.
- 기존에 창업 준비 과정을 설정한 사업에는 `운영 개선으로 전환`을 제공한다. 열기만 해서는 기존 설정을 변경하지 않는다.
- 전환 시 단계별 기록, 직접 쓴 자료, 견적을 유지한다. 아직 저장하지 않은 현재 메모와 자료도 함께 저장한다.
- 이전 완료 기록은 새 과정에서 재확인이 필요한 상태로 표시한다. 실제 운영 완료로 자동 승격하지 않는다.
- AI 대화로 이동할 때에도 재확인 상태를 유지한다. 단순 이동을 이전 완료 기록에 대한 승인으로 취급하지 않는다.
- 운영 범위, 홈페이지, 홍보 단계의 질문과 초안을 현재 문제, 실제 결과, 다음 개선 실험 중심으로 구분했다.
- 모바일에서 AI 대화 연결과 진행 중 저장이 붙어 보이던 배치를 분리하고 하단 고정 버튼을 위한 여백을 확보했다.

### 문서 재생성 저장 경합

- 생성 직전뿐 아니라 저장 시점의 사업 버전과 수정 시각도 비교한다.
- 다른 탭에서 직접 편집/잠금한 문서는 늦게 도착한 생성 결과로 덮지 않는다.
- 다른 항목을 저장한 경우 최신 상태를 다시 읽고 생성 결과만 저장한다. 유료 모델 생성/검토를 재호출하지 않는다.
- 다른 작업자가 동일 개정 문서를 먼저 완성하면 완료된 결과를 유지한다.
- 사업 내용이나 문서 종류가 바뀌면 오래된 맥락의 결과를 저장하지 않는다.
- 저장 재시도는 최대 4회다. 재생성 횟수 기록은 저장 성공 후에만 수행한다.
- 기존 문서의 직전 본문 보존과 수동 수정 보호는 유지한다. 이는 여러 기간의 리포트를 보관하는 기능과 다르다.

### 로컬 격리 저장소

- 브라우저에서 관리 화면은 보이지만 대화 API가 같은 사업을 복원하지 못하는 문제를 재현했다.
- 모듈 내부 메모리 Map이 개발 서버의 라우트 번들/모듈 재평가 때 분리되는 구조를 수정했다. 기존 홈페이지 메모리 저장소와 같이 프로세스 공유 저장소를 사용한다.
- 사업 데이터와 비회원 이전 기록을 함께 공유하며 소유자별 키는 그대로 분리한다.
- 운영 Supabase 경로는 변경하지 않았다. 메모리 모드는 여전히 서버 재시작 시 사라지며 운영 영속 저장소가 아니다.
- 수정 이전에 일부 데이터가 빠진 검증용 사업을 복구된 것으로 간주하지 않았다. 새 검증용 사업으로 화면 간 연결을 다시 확인했다.

## 아직 완성되지 않은 것

- **기간별 운영 리포트:** 지금은 단계별 최신 메모와 자료가 저장된다. 월별/주별 기록을 여러 개 쌓고 비교하는 제품 경로는 없다.
- **별도 리포트 이력:** 창업 계획서를 만든 뒤 운영 단계가 되어도 기존 문서 종류는 유지한다. 운영 맥락의 본문 갱신은 가능하지만 새 운영 리포트를 별도 저장/다운로드하는 기능은 아니다.
- **긴 운영 기록 전달:** 현재 AI 연결은 메모/자료 일부를 URL의 입력 초안으로 전달한다. 긴 기록의 일부가 잘릴 수 있으므로 기간별 리포트에서는 저장된 기록 ID로 서버가 전체 내용을 읽는 방식이 필요하다. 민감한 기록을 URL에 싣지 않는 방향으로 함께 변경해야 한다.
- **운영 과정의 다중 탭 충돌:** 이번 저장 충돌 보완 대상은 생성 문서다. 서로 다른 탭에서 실행 메모/견적을 동시에 바꾸는 전체 상태 충돌은 별도 검증/보완이 필요하다.
- **현재 사업안에서 기존 홈페이지 갱신:** 앞 단계의 `사업 정보 적용`은 홈페이지에 저장된 기준 정보를 다시 적용한다. 새 대화의 최신 사업안을 가져오는 명시적 갱신과 변경 전후 확인은 남아 있다.
- **실서비스 검증:** 실제 AI의 신규/운영 조언 품질, Google 로그인, 테스트 결제, Cloudflare Workflow, PDF/Word/PPT 전체 생성 및 재다운로드는 스테이징에서 검증해야 한다.

## 다음 구현 순서

1. 같은 사업 아래 기간별 운영 기록을 추가한다. 기간, 실제 수치, 고객 의견, 선택한 개선안을 별도 ID와 버전으로 저장하고 동시 편집 충돌을 처리한다.
2. 기록 ID로 대화/생성을 연결한다. 미입력 값과 0, 실제 결과와 목표를 구분하고 원문 전체를 안전하게 전달한다.
3. 이전 기간과의 비교 및 개선안 확인을 제공한다. 검토한 결과를 새 리포트로 저장하고 과거 창업 계획서와 분리해서 보관한다.
4. 최신 사업안 -> 기존 홈페이지 갱신의 변경 전후 확인과 수동 편집 보존을 연결한다.
5. 별도 스테이징에서 인증/권한/결제와 실제 문서 생성/다운로드까지 이어서 검증한다. 그 전에는 정기 리포트나 정상 PPT 제공을 출시 완료로 약속하지 않는다.
