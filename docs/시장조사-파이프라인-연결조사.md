# 시장조사/진단 파이프라인 조사 및 plan-builder 연결 지점 보고서

> **조사 기준**: 코드베이스 직접 확인 (2026-08-22). 코드 수정 없음.
> **중심 파일**: `lib/market/openai-research.ts`
> **목적**: 사업계획서의 시장 세그먼트 / 경쟁 분석 / 문제인식 섹션에 조사 결과와 출처를 전달하는 **최소 변경 지점** 식별

---

## 요약 — 세 줄

1. `researchOfficialMarketEvidence()`는 `ProjectRecord` 전체가 아니라 **필드 8개**만 읽는다. 나머지는 전혀 건드리지 않는다.
2. **plan ↔ project 다리가 이미 있다** — `findProjectIdByPlan(planId, hash)`. 홈페이지 기능이 이미 쓰고 있으며, 같은 방식으로 플랜에 프로젝트 그릇을 붙일 수 있다.
3. 프롬프트 주입 지점은 **`conflicts`와 완전히 대칭**이다. `SectionGenInput`에 `evidence?`를 더하고 `buildUserPrompt()`에 블록 하나를 붙이면 끝난다.

```jsonc
    "JSON 객체 {evidence:[...]}만 출력하세요."
  ]

```

**3중 검증 (환각 방지의 핵심)**

1. `researchOutputSchema.parse()` — Zod, evidence 1~6개, 각 필드 길이·타입 강제
2. `citations(payload)` — 응답의 `action.sources` + `annotations[type=url_citation]`에서 **실제 인용된 URL 집합**을 추출
3. 각 evidence에 대해:
   ```ts
   const citation = cited.get(normalizeUrl(item.sourceUrl));
   if (!citation || !isOfficialEvidenceUrl(citation.url)) return [];   // ← 버림
   ```
   즉 **모델이 적은 URL이 실제 검색 인용 목록에 없으면 그 근거는 통째로 버려진다.**
   저장되는 `sourceUrl`도 모델이 쓴 값이 아니라 **인용 목록의 URL**이다.
4. 하나도 안 남으면 `MARKET_RESEARCH_NO_CITED_EVIDENCE` throw

**출력에 자동으로 붙는 것**

```ts
retrievedAt  = new Date().toISOString()                       // 수집 시각
contentHash  = sha256(JSON.stringify({...item, sourceUrl, retrievedAt}))  // 위변조 확인값
observedAt   = validDate(item.observedAt, retrievedDate)       // 없으면 검색일로 대체
note        += " 통계 기준일은 원문에서 한 번 더 확인해야 하며, 현재 날짜는 검색일입니다."  // 기준일 미확인 시
verification = "needs_review"      // ★ 항상. LLM 경로는 절대 "verified"가 될 수 없음
```

## 2. 데이터 구조

### 2-1. `MarketEvidence` (lib/market/domain.ts:45-85)

```ts
{
  id: string(uuid),
  sourceType: "official_api" | "official_report" | "field_research" | "customer_interview"
            | "competitor_check" | "supplier_quote" | "lease_quote" | "permit_answer",
  title: string,          // 자료 제목
  metric: string,         // 무엇을 잰 값인지 (예: "1인 가구 수")
  value: string,          // 표시용 값 (예: "약 39만 가구")
  numericValue: number | null,   // 단일 숫자로 표현 가능할 때만
  unit: string,
  region: string,
  sourceName: string,     // 기관명
  sourceUrl: string(url | ""),
  observedAt: string(YYYY-MM-DD),   // 통계 기준일
  note: string,           // 이 사업에 적용할 때의 주의점
  verification: "verified" | "user_supplied" | "needs_review",
  verificationMethod: "none" | "official_api",
  sourceExcerpt: string,  // 원문이 무엇을 집계한 자료인지
  retrievedAt: string(ISO datetime | ""),
  contentHash: string(sha256 hex | ""),
  attestation: string,    // HMAC 서명
  isDemo: boolean,
}
```

**`verification: "verified"` 승격 조건** (`superRefine`, :65-83) — 6개 전부 충족해야 함:
`verificationMethod === "official_api"` ∧ `isOfficialEvidenceUrl(sourceUrl)` ∧ `sourceExcerpt.length ≥ 10` ∧ `retrievedAt` ∧ `contentHash` ∧ `attestation` ∧ `!isDemo`

| 경로 | verification | 이유 |
|---|---|---|
| `researchOfficialMarketEvidence` (LLM+웹검색) | **항상 `needs_review`** | `verificationMethod: "none"`, `attestation: ""` |
| `fetchNearbyStores` (data.go.kr 상가정보 API) | **`verified`** | `/market/nearby` 라우트가 `signMarketEvidence()`로 서명 |
| 사용자 수기 입력 | `user_supplied` | — |

> **중요**: 웹검색으로 찾은 근거는 **절대 "공식 확인 완료"가 되지 않는다.** 문서에 실을 때 "확인 필요"로 표기해야 한다.

## 4. 출처(citation) 구조

### 4-1. 출처를 구성하는 필드 5종

| 필드 | 뜻 | 예 |
|---|---|---|
| `sourceName` | 기관·자료명 | "통계청 인구총조사" |
| `sourceUrl` | **검색이 실제 인용한** 원문 주소 | `https://kosis.kr/...` |
| `observedAt` | 통계 기준일 (모르면 검색일) | `2025-12-31` |
| `retrievedAt` | 수집 시각 (ISO) | `2026-08-22T07:14:00.000Z` |
| `contentHash` | sha256 위변조 확인값 | `a3f9...` |

### 4-2. 위변조 방지 — `lib/market/evidence-attestation.ts`

```ts
signMarketEvidence(evidence)    // HMAC-SHA256(EVIDENCE_ATTESTATION_SECRET, 정렬된 JSON)
verifyMarketEvidence(evidence)  // timingSafeEqual
normalizeAttestedMarketWorkspaceInput(input)
   // 클라이언트가 보낸 "verified" 중 서명이 안 맞는 것을 needs_review 로 강등하고
   // verificationMethod/sourceExcerpt/retrievedAt/contentHash/attestation 을 전부 비움
```

### 4-3. 기존 문서에서 출처를 쓰는 방식 — `lib/business-plan/generator.ts` (템플릿, LLM 아님)

**① 검증된 근거만 산문으로** (:133)
```ts
verifiedEvidence.map(item =>
  `${item.metric} ${item.value}${item.unit ? ` ${item.unit}` : ""}(${item.sourceName}, ${item.observedAt || "기준일 확인"})`
).join(" / ")
```
→ `verification === "verified"`만 통과하므로 **웹검색 근거는 산문에 안 들어간다**(현재 구조의 한계).

**② 섹션별 `sources[]`** (:88)
```ts
workspace.evidence.filter(i => Boolean(i.sourceUrl))
  .map(i => ({ name: i.sourceName, url: i.sourceUrl, observedAt: i.observedAt }))
```
`problem`, `scale-up` 섹션에 부착. `solution`은 `competitor_check` 유형만.

**③ 마크다운 부록 "## B. 출처와 확인 상태"** (:173, 렌더 :317)
```
| S01 | 공식 원문 확인 | {title} · {sourceName} | {observedAt} | [원문](url) |
| S02 | 추가 확인      | ...                    | ...          | ...          |
```

> **이 세 함수가 plan-builder에서 그대로 재사용 가능한 "출처 → 문서" 변환기다.**

## 5. plan-builder 연결 — 최소 변경 지점

### 5-0. 이미 존재하는 다리 (가장 중요한 발견)

`app/api/plan/landing/route.ts:108-120` — **홈페이지 기능이 이미 플랜에 프로젝트 그릇을 붙이고 있다**:

```ts
let projectId = await findProjectIdByPlan(plan.id, identity.hash);
if (!projectId) {
  const project = await createProject(
    {
      opportunity: { title: plan.title, planId: plan.id, source: "plan-builder" },
      founderProfile: {},
      paymentStatus: "paid",
      packagePrice: 0,
    },
    identity.hash,
    identity.userId,
  );
  projectId = project.id;
}
```

`findProjectIdByPlan` (`lib/project-repository.ts:199`)는 `opportunity->>planId`로 조회한다.
주석(:191-197)에 *"plan-builder에는 프로젝트가 없으므로 플랜당 하나의 그릇을 만들어 재사용한다"*고 명시되어 있다.

> **즉 "플랜 → 프로젝트" 변환은 이미 구현되어 있고 운영 중이다.**

### 5-1. 경로 A — 프로젝트 그릇 재사용 (DB 변경 0, 기존 저장·출처 UI 전부 재사용)

```text
[새 라우트] POST /api/plan/market-research   { planId }
  ├─ requireGuestIdentity()
  ├─ loadPlanState(hash) → plan 찾기 → state.business 읽기
  ├─ findProjectIdByPlan(planId, hash)  ?? createProject({opportunity:{title, planId, source:"plan-builder"}})
  ├─ getProject(projectId, hash)
  ├─ ★ opportunity/businessSetup 채우기 (아래 5-2 매핑)
  ├─ researchOfficialMarketEvidence(project, openaiConfig)
  ├─ 병합(`${sourceUrl}|${metric}`, 100개 상한) → analyzeLocations → saveMarketWorkspace
  └─ 응답 { evidence, addedCount, citedSourceCount }
```

**필요한 신규 코드**: 라우트 1개(약 60줄).
**기존 코드 수정**: 0
**DB 마이그레이션**: 0 (`projects.market_workspace` 그대로 사용)

**장점**: 위변조 서명·중복 제거·`MarketAnalysis`·기존 출처 표시 컴포넌트를 전부 물려받는다.
**단점**: 플랜마다 `projects` 행이 하나씩 생긴다(홈페이지 기능이 이미 그렇게 하고 있으므로 새 부담은 아님).

| 온라인 쇼핑몰 | `ecommerce` |
| IT·앱·웹 | `digital_service` |
| 교육·강의 / 서비스·용역 / 콘텐츠·크리에이터 | `professional_service` |
| 제조·생산 | `manufacturing` |
| 기타 | `undecided` (함수가 이 문자열을 그대로 프롬프트에 넣으므로 안전) |

> **중요**: 프롬프트 품질은 `customer`·`oneLiner`·`sector`에 좌우된다.
> 따라서 **`market/segments`·`overview/problem` 섹션을 답한 뒤**에 조사를 돌려야 의미 있는 결과가 나온다.

### 5-3. 경로 B — plan_states 안에 보관 (프로젝트 없이, 더 가벼움)

`plan.answers`는 **섹션 키 화이트리스트가 없다** (`plan-server-store.ts:81` — `typeof object` 검사만).
이미 같은 기법을 쓰는 선례가 있다:

```ts
// lib/plan-builder/financials.ts:219
export const FINANCIAL_OVERRIDE_KEY = "financials/__review";
// 주석: "실제 질문 섹션이 아니라 보정값 저장 전용이므로 진행률·문서에는 포함되지 않는다."
```

동일하게 `MARKET_EVIDENCE_KEY = "market/__evidence"`를 두면:

- **DB 마이그레이션 0** — `plan_states.data` jsonb 안에 그대로 저장
- **진행률 영향 0** — `PlanOverview.tsx:138-147`이 `chapters`(blueprint 기준)만 순회하므로 가상 키는 세지 않음
- **답변 이어받기에 자동 포함** — `createPlan(..., {inheritAnswers:true})`가 `answers`를 통째로 복사
- 이미 `allAnswers`가 생성 API로 전달되므로(`generate/route.ts` body) **추가 전달 배관 불필요**

**단점**: `MarketEvidence`의 서명 검증(`normalizeAttestedMarketWorkspaceInput`)이 이 경로에는 걸려 있지 않다.
다만 웹검색 근거는 어차피 `needs_review`라 서명 대상이 아니므로 실질 위험은 낮다.
(`plan_states`는 정책 0개 service-role 전용이라 클라이언트 직접 쓰기도 불가)

### 5-4. 프롬프트 주입 — `conflicts`와 완전히 대칭

현재 `SectionGenInput`(`lib/plan-builder/section-generator.ts:59-84`)은 이미 같은 모양의 선택 필드를 갖고 있다:

```ts
conflicts?: Array<{ title: string; detail: string }>;
```

여기에 한 줄을 더하면 된다:

```ts
/** 확인된 공식 시장 근거 — 이 출처만 인용할 수 있다 */
evidence?: Array<{ metric: string; value: string; sourceName: string; sourceUrl: string; observedAt: string; note: string }>;
```

`buildUserPrompt()`에 `formatConflicts()`와 같은 형태의 블록을 추가:

```text
[확인된 공식 시장 근거 — 검색으로 원문을 확인한 값]
- {metric}: {value} ({sourceName}, {observedAt}) {sourceUrl}
  적용 시 주의: {note}

위 수치는 공식 원문에서 확인한 값입니다. 본문에 인용할 때는 반드시 기관명과 기준일을 함께 적으세요.
목록에 없는 수치를 새로 만들지 마세요.
이 값들은 아직 담당자가 재확인하지 않은 상태이므로 '원문 재확인 필요'임을 한 번만 밝히세요.
```

## 6. 제약과 주의 (실행 전 알아야 할 것)

| 항목 | 내용 |
|---|---|
| **OpenAI 전용** | `web_search` 도구는 OpenAI Responses API 기능. plan-builder는 `resolveLLMConfig(hash,"anthropic")`로 Claude를 쓰므로, 조사만 **별도 OpenAI 키**가 필요하다. 키 없으면 `409 OPENAI_NOT_CONNECTED`. 로컬 `.env.local`에 AI 키가 없어 **로컬 검증 불가, 운영에서만 확인 가능**. |
| **소요 시간** | 최대 150초. `maxDuration = 180`. 섹션 생성(180초)과 합치면 사용자 대기가 길다 — 위저드 흐름에 넣으려면 큐/백그라운드가 필요할 수 있다. |
| **verified 승격 불가** | 웹검색 근거는 항상 `needs_review`. 문서에 "공식 확인 완료"로 표기하면 안 된다. `verified`는 `data.go.kr` 상가정보 API(`fetchNearbyStores`) 경로에서만 나온다. |
| **결과 0건 가능** | 인용 검증에서 전부 탈락하면 `MARKET_RESEARCH_NO_CITED_EVIDENCE`. 라우트는 *"사업 지역이나 고객 범위를 더 구체적으로 정한 뒤 다시 시도"* 안내를 준다. |
| **비용** | 호출당 4,000 출력 토큰 + `search_context_size: "high"` 웹검색. 섹션 생성(25회)과 별개 비용. **plan-builder에는 이 기능의 쿼터·과금이 없다** — `regen-quota`처럼 별도 카운터가 필요하다. |
| **보안 모델 차이** | `projects`는 RLS 정책 있음(owner_id 기반), `plan_states`는 정책 0개(service-role 전용). 경로 A를 쓰면 두 모델이 한 기능에 섞인다. |
| **`saveMarketWorkspace` 부작용** | 호출 시 `business_plan = null`로 무효화한다(`project-repository.ts:730`). plan-builder는 `projects.business_plan`을 쓰지 않으므로 무해하지만, 홈페이지용으로 만든 같은 프로젝트 행을 공유한다는 점은 인지해야 한다. |
| **`generateBusinessPlan` 재사용은 비권장** | `project.stages[]`, `businessSetup.financial`, `businessAssessment.financial`을 읽는다. plan-builder에는 이 데이터가 없어 대부분 폴백 문구가 나온다. **출처 변환 3함수만 참고**하는 편이 낫다. |
| **죽은 UI 있음** | `components/market-plan-panel.tsx`(수기 근거 입력·주변 상가 조회·플랜 뷰어)와 `RegionalCoveragePanel`은 `app/page.tsx`에서 import만 되고 **렌더되지 않는다**. 근거 입력/표시 UI를 새로 만들기 전에 이 코드를 먼저 볼 것. |

## 7. 추천 순서 (최소 변경 → 확장)

1. **1단계 — 프롬프트 배관만** (기능 위험 0)
   `SectionGenInput.evidence?` + `buildUserPrompt()` 블록 + 시스템 프롬프트 예외 + 두 생성 경로 전달.
   근거는 아직 없어도 되며, `undefined`면 아무 일도 일어나지 않는다(`conflicts`와 동일).

2. **2단계 — 저장소 결정**
   경로 B(`market/__evidence` 가상 키)가 DB 변경 0이고 답변 이어받기까지 자동으로 따라온다.
   위변조 서명이 필요해지면 그때 경로 A로 옮긴다.

3. **3단계 — 조사 라우트**
   `POST /api/plan/market-research` — 5-2 매핑으로 duck type 객체를 만들어 `researchOfficialMarketEvidence` 호출.
   `researchOfficialMarketEvidence`의 시그니처를 `ProjectRecord` → 8필드 인터페이스로 **넓히면**(narrowing이 아니라 widening) 기존 호출부는 그대로 동작한다.

4. **4단계 — UI**
   `SectionWizard`의 `market/segments`·`market/competitors`·`overview/problem`에 "공식 근거 찾기" 버튼.
   기존 `loadSuggest()` 패턴 그대로.

5. **5단계 — 출처 표기**
   `generator.ts`의 출처 표 함수를 참고해 문서 말미에 "출처와 확인 상태" 표를 붙인다.
   PDF/DOCX는 마크다운 표를 이미 렌더하므로 추가 작업 없음.
