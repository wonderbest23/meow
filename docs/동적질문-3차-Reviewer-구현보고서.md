## 2. ReviewReport 실제 Schema

```ts
type ReviewSeverity = "critical" | "warning" | "improvement";
type ReviewCategory =
  | "business_model" | "customer" | "problem_solution" | "competition" | "marketing"
  | "operation" | "finance" | "market_evidence" | "fact_safety" | "consistency" | "writing";

interface ReviewIssue {
  id: string;                    // det-1… / ai-1…
  severity: ReviewSeverity;
  category: ReviewCategory;
  sectionKey?: string;           // 아는 섹션 키만 남긴다(모르는 키는 제거 → 빈 화면 방지)
  title: string;
  problem: string;               // 무엇이 문제인가
  whyItMatters: string;          // 왜 중요한가
  evidence: string[];            // 본문 인용·계산값·사용자 답변
  recommendation: string;        // 무엇을 확인/고치면 되는가
  requiresUserInput: boolean;
  autoFixable: boolean;
  origin: "deterministic" | "ai";   // 사양에 없던 필드 — 아래 §5 참조
}

interface ReviewDimension { id: string; label: string; score: number /*0~5*/; reason: string }

interface BusinessPlanReview {
  version: string;
  overallQualityScore: number;   // 0~100. AI 가 실패하면 -1(= 미산출)
  dimensions: ReviewDimension[]; // 7개 고정
  issues: ReviewIssue[];
  strengths: string[];
  topPriorities: string[];
  summary: string;
}
```

**사양에서 바꾼 것 하나**: `origin` 필드를 추가했습니다. 코드가 계산으로 확정한 문제와 AI 판단을 화면에서 구분해야, 사용자가 "계산으로 확인" 배지가 붙은 것을 먼저 신뢰할 수 있습니다. 병합 시 중복 제거의 기준이기도 합니다.

**평가 차원 7개**(각 0~5): 사업 구조 명확성 · 시장·고객 근거 · 차별성 · 실행 가능성 · 수익성·재무 논리 · 마케팅 현실성 · 문서 일관성·신뢰성.

## 4. deterministic 검사와 Reviewer 의 관계

코드가 **확실히 아는 것은 LLM 에게 묻지 않습니다.** 먼저 계산하고, 결과를 "검증된 사실"로 프롬프트에 넣습니다.

| 확정 검사 | 판정 | 심각도 |
|---|---|---|
| 공헌이익 ≤ 0 | `calculateFinancials().unit` | **critical** |
| 손익분기 > 목표 판매량 | 같은 계산 | 2배 이상 critical / 그 외 warning |
| 목표 판매량 > 운영 상한 | `monthlyCapacity` 또는 정원×횟수(확정 지표) | **critical** |
| 초기투자 > 0 인데 조달 답변 없음 | 답변 + Context | warning |
| 판매 목표 있는데 홍보 채널·예산 모두 없음 | Context | warning |
| 정합성 검사 15종 | `consistency.ts` | conflict→critical / check→warning |
| 위저드 ↔ VERIFY 충돌 | `PlanBusinessContext.conflicts` | warning |
| 미확정 항목 | `context.unknowns` | improvement |
| 공식 근거 0건 | evidence | improvement |

프롬프트 규칙: **"반박하거나 '문제 없다'고 판단하지 마세요. 같은 문제를 다시 만들어 중복시키지도 마세요."**
병합(`mergeIssues`)에서도 ① 확정 문제를 앞에 두고 ② `consistency` 카테고리의 AI 문제는 전부 버리고 ③ 같은 카테고리·같은 섹션을 코드가 이미 확정했으면 AI 문제를 중복으로 제거합니다.

**운영 실측**: 5~6건 중 deterministic 3건 + AI 2~3건. 중복 0건.

## 6. 저장 · 낡음 판정

`plan.answers["__review"]` 가상 키 — **DB 마이그레이션 없음**(분석과 같은 방식).

```ts
{ version: "general-review-v1", reviewedAt, planId, contentHash, result }
```

**낡음(stale) 판정 3단**:
1. `version` 불일치 → 무효
2. `record.planId !== plan.id` → 무효 (답변 이어받기로 복사돼 와도 여기서 걸림)
3. `contentHash` 불일치 → **stale** (화면에 "본문을 고치기 전에 한 검토" 배너)

`contentHash` 는 의존성 없는 FNV-1a 32bit로, **정렬된 섹션 키 + 본문 전체**를 해싱합니다. 키 순서가 달라도 같은 값, 본문 한 글자만 바뀌어도 다른 값, 섹션이 늘거나 줄어도 다른 값(테스트로 고정).

사양이 지적한 **답변 이어받기 문제는 두 겹으로 막았습니다**: `createPlan()` 이 `__review` 를 복사하지 않고(원인 제거), 읽을 때 `planId` 를 대조합니다(안전망). 겸사겸사 `__analysis`·`__review` 를 '답변 N개' 집계에서 빼, 사용자에게 보이던 개수 부풀림도 없앴습니다.

두 번째 AI 지적(사업주 노동의 기회비용)은 **계산된 재무를 정확히 인용하면서**(179건·3,685만원 모두 엔진 값) 그 계산이 놓친 것을 짚은, 컨설턴트다운 발견입니다. 숫자를 새로 만들지 않았습니다.

`critical` 은 이 문서에서 0건이었습니다 — 억지로 만들지 말라는 지시가 지켜졌습니다.

## 10. false positive 사례 (발견 → 수정 → 재검증)

**1차 실행에서 잘못 잡은 것 1건**:

> `fact_safety` / "확인되지 않은 사용자 답변 값 인용" — "이 섹션은 `knows_breakeven=no`, `asset_own=no`, `needs_assets=yes` 등을 구체적 사실로 인용하지만, 제공된 확정 사실 목록에는 이 값들이 존재하지 않습니다."

**이 값들은 실제 사용자 답변입니다.** Writer 는 섹션 원문 답변을 받는데 Reviewer 에게는 골라 담은 `PlanBusinessContext` 요약만 갔습니다. 사실 대조의 기준선이 Writer 보다 좁으면 **정상 인용이 전부 환각으로 잡힙니다.**

→ `[사용자가 질문에 답한 원문 — 전부 확정 사실입니다]` 블록을 추가(커밋 `6fe5ace`). 재실행 결과 **`fact_safety` 0건**, 대신 위 §9의 실질적 지적 3건이 나왔습니다. 입력은 37,004 → 39,010 토큰(+2,006).

> 2차 후속 패치의 지표 유실과 **같은 계열의 버그**입니다: 하위 시스템에 주는 사실 목록이 상위 시스템이 본 것보다 좁으면, 정상 서술이 문제로 둔갑합니다.

## 14. 자동 Repair 로 넘길 수 있는 비율

실측 5~6건 기준:

| 구분 | 비율 | 예 |
|---|---|---|
| `requiresUserInput = true` | **약 70%** | 홍보 채널·예산, 사업주 인건비 가정, 운영자금, 미확정 항목 |
| `autoFixable = true` | **약 10%** | 통계 과잉해석 표현 완화, 반복 문단 정리 |
| 둘 다 false | 약 20% | 공식 근거 0건(사용자가 버튼을 눌러야 함) |

deterministic 문제는 거의 전부 `requiresUserInput` 입니다 — 코드가 확정할 수 있는 문제는 대개 **정보가 없거나 어긋난** 것이라 사람이 답해야 풀립니다. **자동 Repair 로 문서만 고쳐 해결되는 비율은 낮습니다.** 4차에서 Repair 를 만든다면 대상은 `writing`·`market_evidence` 표현 완화 정도로 좁게 잡는 편이 안전합니다.

## 15. 남은 한계

1. **표본 1개 문서**. 5종 사업 각각의 실제 25섹션 문서를 만들려면 생성 125회가 필요해 이번에는 실측을 실제 플랜 1건(15섹션)으로 했습니다. 나머지 케이스는 fixture 테스트로 덮었습니다.
2. **요약에 '정책자금 심사' 표현이 한 번 등장**했습니다(문서 자체가 정책자금을 다뤄서). 선정 가능성을 예측한 것은 아니지만, 심사 통과 가능성으로 읽힐 여지가 있어 프롬프트에 금지 표현을 더 넣을지 다음 회차에서 판단이 필요합니다.
3. **응답 90~113초**. 화면은 진행 표시로 버티지만 체감이 깁니다. 스트리밍이나 부분 표시는 이번 범위 밖입니다.
4. `overallQualityScore` 는 **모델이 매깁니다**. 같은 문서를 두 번 검토해 62/64 가 나왔습니다(±2). 절대값보다 항목별 지적을 보게 하는 UI 구성이라 문제는 작지만, 점수 안정화는 과제입니다.
5. digest 경로(60,000자 초과)는 테스트로만 검증했고 운영 실측은 없습니다.
