# 대화 중심 사업 기획: 2026-09-06 구현 기록

새로운 아이디어 구체화와 산술 검사의 후속 구현은 [사업 설계 고도화 기록](./business-design-rollout.md)을 참고한다. 실제 AI 품질 검증과 단계별 남은 작업을 별도로 구분했다.

## 제품 범위

- 새 이용자는 `/plan/chat`에서 대화로 시작한다. `/plan/start`도 같은 대화 화면이다.
- 아이디어 탐색, 정해진 아이디어 구체화, 운영 중인 사업 개선을 구분한다.
- 초기 핵심 상품은 일반 사업계획서와 사업 운영·개선 계획서다. 신규 흐름에서는 투자 심사나 지원사업 선정 가능성을 평가하지 않는다.
- 홈페이지 제작은 문서를 만든 다음 선택하는 기존 부가 기능으로 남긴다.
- 기존 사용자의 예전 계획서와 편집 화면은 삭제하지 않는다.

## 구현된 처리 순서

1. 대화에서 이미 제공한 내용을 추출한다. 한 번에 하나만 질문하며 모르는 비용이나 실적을 필수 입력으로 요구하지 않는다.
2. 사업이 정해지면 고객·상품·제안 가격·판매 방법·운영 범위를 공통 사업안으로 정리한다. 빠진 내용은 별도 기획 호출로 보완하고 다른 문서가 각각 다른 사업을 만들지 않도록 먼저 저장한다.
3. 사용자 제공 정보와 AI 제안을 분리한다. 사용자 값은 원문 인용이 일치해야 인정한다. 원문에 없는 실적·경력은 제안으로 바꾸어 끼워 넣지도 않는다.
4. 문서 작성과 사실·계산·실행 가능성 검토를 분리한다. 문제 발견 시 한 번 수정하고 다시 검토한다. 실패하거나 잘린 응답은 완료 문서로 저장하지 않는다.
5. 문서는 기존 Cloudflare Workflow에서 항목별로 생성·저장한다. 문서 제작 진행률은 저장된 항목 수이며 토큰 생성률이 아니다.
6. 대화 수정은 공통 정보에 반영한다. 인사 등 내용 변화가 없는 대화에서는 문서 재작성 버전을 올리지 않는다. 직접 편집한 본문은 덮어쓰지 않고 검토 필요를 알린다.
7. PDF·Word·PPT는 대화형 사업의 경우 서버에 저장한 동일 계획서에서 제작한다. 자동 생성 본문이 이전 버전이면 최신 내용 반영을 안내한다.
8. PPT는 사업 소개/운영 회의에 맞춘 구성을 사용한다. 요약에 표와 본문 후반을 포함하고, 슬라이드별 원천 계획서 항목을 확인해 발표자 노트에 보관한다.

## 정확성의 범위

- 사용자 제공 정보는 독립적으로 확인된 사실이 아니다.
- 제안 가격·운영 범위는 검토할 제안이다. 시장 표준, 실제 매출, 성공 가능성을 뜻하지 않는다.
- 미입력 비용은 0원으로 바꾸지 않는다. 숫자가 정해진 경우에만 기존 계산 엔진으로 계산하며 영업손익을 현금잔액으로 표현하지 않는다.
- 외부 근거가 없으면 시장규모·성장률·실제 고객 인터뷰·법령·세율을 새로 확인했다고 쓰지 않는다.
- 별도 LLM 검토는 오류를 줄이기 위한 절차이며 사실 검증이나 전문가 검토를 대체하지 않는다.
- 통합 시장 데이터, 세무사 연결, 사업자등록 대행, 투자·정부지원 제출 인증은 이번 구현 범위가 아니다.

## 모델과 운영 설정

- `OPENAI_API_KEY`: 서버 비밀키. 클라이언트에 넣지 않는다.
- `PLANNING_MODEL=gpt-6-astra`: 새 사업 대화·문서·검토·PPT용 모델. 기존 고객지원 등에는 전역 적용하지 않는다.
- OpenAI 설정이 없으면 기존 Anthropic 설정을 사용할 수 있다. 통합 클라이언트의 대체 공급자 사용도 남아 있으므로 실제 실행 모델은 사용량 로그로 확인해야 한다.
- Supabase의 기존 `plan_states` 저장 구조를 사용한다. 추가 테이블 마이그레이션은 없다.
- 전체 문서 제작에는 기존 `PLAN_SECTIONS_WORKFLOW`, `WORKER_SELF_REFERENCE`, 서버 서명용 Supabase 키가 필요하다.
- 이 로컬 환경에는 OpenAI/Anthropic 키가 없었다. 실제 Astra 응답 품질과 운영 계정의 해당 모델 접근은 아직 검증하지 않았다.
- 로컬 Next 개발 모드에서는 자체 Workflow 바인딩을 사용할 수 없다. 이 경우 대화를 저장하고 제작 서버 미연결을 안내한다. '창을 닫아도 완료' 안내는 서버 작업을 등록한 후에만 보인다.

## 검증

- `scripts/business-coach.test.ts`: 진입 유형, 사실 인용, 사용자 수정 우선, 문서 버전, 비용 미입력, 저장 소유권, 작성 후 검토, 잘린 응답 차단, PPT 원천 항목.
- `scripts/business-coach-attachment.test.ts`: Word 추출, XML 엔터티 거부, 업로드 크기, 압축 해제 크기 제한.
- `scripts/business-coach-concurrency.test.ts`: 저장 직전 동시 변경을 감지해 다시 읽고 다른 문서를 보존한다. DB 읽기 오류를 빈 문서로 처리하지 않는다. 테스트 DB 응답을 사용한다.
- `scripts/business-coach-ui.test.ts`: 320/390/1440px에서 대화 입력·전송·긴 문장·가로 넘침·제작 오류 안내. AI 응답은 테스트용이다.
- 실제 AI 결과물 품질을 통과했다고 해석하면 안 된다. 화면 스크린샷의 본문도 테스트 응답이다.
- Workflow 제한시간 설정은 [Cloudflare의 단계 설정 문서](https://developers.cloudflare.com/workflows/build/step-context/)를 기준으로 기존 로컬 타입 정의에 추가했다.

## 운영 배포 전 확인

1. 운영과 분리된 검증 환경에서 Astra 접근을 확인한다. 실패 시 모델을 조용히 바꾸어 품질 검증 통과로 처리하지 않는다.
2. 아이디어 없음, 개인 서비스, 온라인 상품, 오프라인 매장, 소프트웨어, 기존 사업 개선을 각각 실행한다.
3. 새 사업안에서 9개 본문 전체를 생성하고 PDF·Word·PPT를 실제로 열어 읽는다. 예산·상품 가격·고객·운영 범위가 서로 일치하는지 대조한다.
4. 사용자 수정 후 재작성, 직접 편집한 본문 보존, 다른 탭의 동시 수정, 생성 중 브라우저 종료 후 완료를 운영 저장소/Workflow에서 검증한다.
5. 사용 토큰·작성 시간·실패율을 수집한다. 사용자 입력 누락이 아니라 작성/검토 실패 때문에 차단된 경우를 따로 집계한다.
6. 결제 전후 권한과 전체 제작 복귀를 테스트한다. 실제 승인이나 환불을 테스트 목적으로 임의 실행하지 않는다.
7. 실제 결과물과 기존 샘플의 차이를 검토한 뒤 신규 흐름을 운영에 공개한다.
