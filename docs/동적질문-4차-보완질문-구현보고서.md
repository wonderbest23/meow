## 2. resolution schema

```ts
type ResolutionType = "answer" | "market_research" | "manual_edit" | "auto_rewrite";

interface ResolutionSlotRef {
  id: string;              // 화이트리스트 목표 id
  sectionKey?: string;     // 기존 질문 칸
  qid?: string;
  analyzerSlot?: string;   // __analysis.slots
}

interface IssueResolution {
  type: ResolutionType;
  slots?: ResolutionSlotRef[];      // 최대 3
  affectedSections?: string[];      // 다시 써야 할 섹션
}

interface ReviewIssue { …; resolution?: IssueResolution }
```

**Reviewer LLM 은 `sectionKey`·`qid` 를 고르지 않습니다.** 프롬프트는 3차 그대로이고, 연결은 전부 코드가 합니다(§18 요구).

## 3. issue → slot/question 매핑

### 코드가 만든 확정 문제 — 만들 때 함께 붙인다

| 문제 | 연결되는 질문 |
|---|---|
| 홍보 채널·예산 없음 | `promo_channels` + `promo_budget` |
| 공헌이익 ≤ 0 | `unit_price` + `variable_per_unit` |
| 손익분기 > 목표 | `fixed_total` + `monthly_volume` + `unit_price` |
| 목표 > 운영 상한 | `growth_ceiling` + `monthly_volume` |
| 초기투자만 있고 조달 없음 | `funding_sources` + `use_of_funds` |
| 정합성 충돌 | 어긋난 `qid` 중 등록된 것 |
| 위저드↔VERIFY 충돌 | 고객→`first_target` / 상품→`unit_price` |
| 미확정 항목 | 그 슬롯들(별칭 변환 후) |
| 공식 근거 0건 | **`market_research`** (질문 아님) |

### AI 가 찾은 문제 — 키워드 → 카테고리 순으로 코드가 좁힌다

```
market_evidence           → market_research
writing                   → auto_rewrite
requiresUserInput = false → manual_edit
그 외 → 키워드 14종(인건비·자금조달·채널·차별·정원·방문자·1인 운영·capacity·경력·단가…)
        → 없으면 카테고리 기본값 → 없으면 manual_edit
```

**운영 실측 매핑 결과** (실제 AI 문제):

## 6. 답변 저장

새 저장 시스템 없음. 두 곳만 씁니다.

| 종류 | 저장 위치 |
|---|---|
| 기존 질문 | `plan.answers[sectionKey][qid]` |
| 질문팩 슬롯 | `plan.answers["__analysis"].slots[slotId]` |

- **분기 게이트를 함께 켭니다**: `promo_budget` 을 저장하면 `has_promo_budget: "yes"` 도 같이 넣습니다. 안 그러면 위저드에서 답이 숨습니다. (실측 확인)
- **'아직 모르겠어요'**: 분석 슬롯은 `{value: null, status: "unknown"}`, 기존 질문 칸은 비워 둡니다. **값을 만들지 않습니다.**
- 이미 답이 있으면 미리 채워 고칠 수 있게 합니다.

## 7. 부분 재생성

- `affectedSections` ∩ **이 플랜 유형에 있는 섹션** ∩ **본문이 있는 섹션** ∩ **잠그지 않고 직접 고치지 않은 섹션**
- 기존 `/api/plan/generate` 를 그대로 호출합니다 — 새 우회 경로 없음. 재생성 쿼터·저장(`saveSection`)·되돌리기(`keepPrevious`) 정책 그대로.
- 잠금·수정한 섹션은 건너뛰고 화면에 알립니다("직접 고쳤거나 잠근 N개는 건드리지 않아요").
- 재생성 전 안내: "이미 만들어진 본문을 다시 쓰면 재생성 횟수가 사용됩니다."

## 8. stale 동작

3차의 `contentHash` 구조를 그대로 씁니다. 부분 재생성으로 본문이 바뀌면 해시가 달라져 자동으로 `stale` 이 되고, 패널에 **"이 검토는 본문을 고치기 전에 한 것이에요"** 배너가 뜹니다. **Reviewer 를 자동 재호출하지 않습니다** — 비용과 대기시간 때문에 [다시 검토하기] 는 사용자 행동으로 둡니다. (실측 확인)

## 12. 실측에서 잡은 문제 2건

### ① 눌러도 빈 화면인 버튼 (`d50b951`)

미확정 항목 문제의 슬롯 id 는 분석 슬롯 이름(`problem`·`customer`·`classPrice`)인데 목표는 질문 이름(`problems`·`first_target`·`unit_price`)을 씁니다. 매칭이 안 돼 `slots: []` 인 채 "답변 추가하기" 가 떴고, 눌러도 아무것도 나오지 않았습니다.
→ 별칭 16개 추가 + 슬롯이 비면 `manual_edit` 으로 강등.

### ② 다시 썼는데 본문이 그대로 (`66b1779`, `b316b4a`)

홍보 채널을 답하고 '한눈에 보기'를 다시 썼는데 채널이 본문에 없었습니다. **원인 두 가지**:

1. `overview/summary` 맥락 규칙이 `marketing.acquisitionModel`(AI 추정)만 받고 사용자의 실제 답 `marketing.channels` 는 받지 않았습니다. → 규칙에 추가.
2. 이 플랜에는 `__analysis` 가 없어(분석 도입 이전 문서) **맥락 블록이 통째로 빠졌습니다.** 2차의 "분석 없는 플랜은 프롬프트 바이트 동일" 보장 때문입니다. → 일반 생성 경로는 그대로 두고, **보완 재생성에서만** `withContext: true` 로 맥락을 켭니다.

수정 후 재실행에서 `| 홍보 채널 | 지역 커뮤니티·맘카페, 인스타그램 |` 이 실제로 들어갔습니다.

> 두 건 모두 "연결은 했는데 값이 흐르지 않는" 같은 계열입니다. 2차 지표 유실·3차 false positive 와 함께, **경계를 넘길 때 상대가 실제로 그 값을 받는지 확인해야 한다**는 교훈이 반복됩니다.

|---|---:|---|
| `answer` (질문 연결) | 5 | **이번에 해결 경로가 생김** |
| `market_research` | 1 | 기존 공식자료 검색으로 |
| `auto_rewrite` | 0~1 | **다음 단계** — 표현 완화·반복 제거 |
| `manual_edit` | 0~1 | 편집기로 |

`auto_rewrite` 는 `resolution.type` 으로 표시만 해 두고 실제 자동 수정은 만들지 않았습니다(§14 요구). 3차 보고서에서 추정한 대로 자동 수정 대상은 전체의 10% 안팎이고, 대부분은 **정보가 없어서 생긴 문제**라 사람이 답해야 풀립니다 — 그래서 이번 작업의 방향(질문 연결)이 실효가 큽니다.

---

## 15. 남은 한계

1. **키워드 매칭의 한계**. `resolveAiIssue` 는 정규식 14종에 기댑니다. "맞춤형 **경험**"이 대표자 경력 규칙에 걸리는 오탐을 하나 잡아 고쳤지만, 새로운 표현이 나오면 또 빗나갈 수 있습니다. 빗나가면 `manual_edit` 으로 떨어져 안전하게 실패합니다.
2. **한 문제에 한 번만**. 답변 후 같은 문제 카드는 그대로 남습니다(검토를 다시 해야 사라짐). 의도된 동작이지만 사용자가 "고쳤는데 왜 남아 있지" 라고 느낄 수 있습니다.
3. **재생성 149초**. 3개 섹션을 순차 처리합니다. 병렬화는 이번 범위 밖입니다.
4. **`withContext` 는 보완 재생성에만**. 옛 플랜을 일반 경로로 다시 쓰면 여전히 맥락이 빠집니다. 옛 플랜 전체를 맥락 경로로 옮길지는 별도 판단이 필요합니다.
5. 실측은 **문제 1건 · 플랜 1개**입니다. 다른 목표(차별점·인건비·자금조달)의 재생성 품질은 아직 실측하지 않았습니다.

---

## 16. 다음 단계

1. **`auto_rewrite` 실제 구현** — 표현 완화(통계 과잉해석)·반복 제거로 좁게. 원천 자료를 바꾸지 않고 문장만 손보는 것이라 안전합니다.
2. **답변한 문제 표시** — 검토를 다시 하기 전까지 "답변함" 배지를 달아 §15-2 를 완화.
3. **다른 목표 실측** — 차별점·인건비·자금조달로 각각 한 번씩 끝까지 돌려 재생성 품질 확인.
4. **재생성 병렬화** — 3개를 동시에 보내면 149초 → 60초 수준.
