## 0. 먼저 바로잡을 사실 — "138개"의 실제 구성

조사 결과 흔히 쓰던 "138개 질문"은 다음으로 나뉜다.

| 구분 | 개수 | 비고 |
|---|---:|---|
| `SECTION_QUESTIONS` — 25개 섹션의 공통 질문 | **131** | 모든 사용자가 유형 필터를 거쳐 만난다 |

| **사용자가 실제로 만날 수 있는 총합** | **137** | |

이 보고서의 분류표는 **137개**를 전부 다룬다.

또한 현재 구조에서 이미 작동 중인 축소 장치가 있다는 점을 먼저 밝힌다 — 이것을 버리고 새로 만들 필요가 없다.

- `showWhen` 조건부 분기 (현재 **30개** 질문이 분기 뒤에 숨어 있다)
- `weight: "core" | "detail"` 등급
- `TYPE_ADJUST`의 `drop` / `coreOnly` / `requiredOnly` — 예: "간단 · 사업계획서"는 10섹션 + core 질문만
- 모듈 로드 시 **분기 무결성 검증** (부모 질문이 필터로 빠지면 `throw`)

> **설계 원칙**: 새 시스템은 이 뼈대를 **대체하지 않고 앞단에 얹는다.**
> 138개를 폐기하는 것이 아니라, **"묻는 순서와 묻지 않을 것"을 AI가 정하게** 한다.

## 1-4. 확인된 중복 쌍 (통합 1순위)

이미 `consistency.ts`가 **충돌로 검사하고 있는 쌍**은, 애초에 두 번 물었기 때문에 생긴 문제다.

| 중복 쌍 | 현재 상태 | 제안 |
|---|---|---|
| `market/products.price_value` ↔ `financials/revenue.unit_price` | 정합성 검사 #3이 "상품 가격과 재무 판매가가 다릅니다"로 잡음 | **한 번만 묻고 두 섹션이 공유** |

> 통합하면 **정합성 검사 3종이 발동할 일 자체가 사라진다.** 검사 코드는 옛 데이터를 위해 남긴다.

## 1-5. 시장조사 연결로 이미 무의미해진 질문

2026-08-22 공식 시장근거 검색이 붙으면서 다음 두 질문은 **역할이 사라졌다.**

- `market_size_known` — "이 그룹의 규모를 파악하셨나요?"
- `market_size` — "파악한 규모와 출처를 적어주세요."

`MarketEvidence`가 `metric`·`value`·`sourceName`·`observedAt`·`sourceUrl`을 **구조화해서** 가져오므로,
자유 서술로 받은 시장 규모는 검증도 안 되고 문서에서 쓰이지도 않는다. **삭제 1순위.**

# 2. Business Analyzer 설계

## 2-1. 역할

사업 아이디어 자유 입력 **직후 1회** 실행. 사업 구조를 구조화하고, **아는 것과 모르는 것을 가른다.**

```
입력: 자유 서술 2~5줄 (+ 이미 있는 사업 정보: 업종·지역이 있으면 힌트로)
출력: BusinessAnalysis (JSON) — 모든 필드에 status 부착
호출: LLM 1회 (Gap Analyzer 결과 포함)
```

## 2-2. 절대 규칙 — 추론과 사실의 분리

현재 시스템의 리얼리티 게이트 철학을 그대로 잇는다.

```
status: "confirmed"   사용자가 직접 말했거나 답한 것
status: "inferred"    AI가 추론한 것 — 사용자 확인 전까지 사실이 아니다
status: "unknown"     아직 모름 — 질문 대상
```

- `inferred` 값은 **사업계획서 본문에 사실처럼 쓰이지 않는다.**
- `inferred` → `confirmed` 승격은 **사용자가 "맞아요"를 눌렀을 때만.**
- 숫자(`unknown`)를 AI가 임의로 채우지 않는다. "아직 모르겠어요"도 정상 답변이다.

이는 `MarketEvidence.verification`(`verified`/`user_supplied`/`needs_review`)과 같은 발상이며,
`section-generator.ts`가 이미 `[해결되지 않은 답변 충돌]`을 다루는 방식과 대칭이다.

# 4. Gap Analyzer 설계

## 4-1. 역할

"이 사업의 사업계획서를 쓰려면 **아직 무엇이 없는가**"를 계산한다. **규칙 기반 우선, LLM은 보조.**

## 4-2. 입력

```
BusinessAnalysis (§2)  +  기존 plan.answers  +  선택된 태그  +  planType(섹션 목록)
```

## 4-3. 계산 (LLM 없이 가능한 부분)

```ts
requiredSlots = CORE_SLOTS                       // 모든 사업 공통 (§6 CORE)
              ∪ packSlots(modelTags)             // 사업모델별 (§7)
              ∪ conditionalSlots(opTags, answers)// 조건부
              ∩ sectionsForType(planType)        // 이 문서 유형이 쓰는 섹션만

filledSlots   = analysis.confirmed ∪ answers(비어있지 않은 것)
inferredSlots = analysis.inferred                // 확인 대기
gaps          = requiredSlots − filledSlots
```

각 gap에 **가중치**를 준다.

| 등급 | 뜻 | 예 |
|---|---|---|
| `blocking` | 없으면 문서의 핵심이 성립 안 됨 | 재무 6숫자, `first_target`, `differentiator` |
| `important` | 없으면 해당 섹션이 얕아짐 | `problem_freq`, `budget`, `runway` |
| `optional` | 있으면 좋음 | `story`, `asset_own` |

**충족률** = `blocking` 충족 비율 (가중 평균, §12에서 종료 판정에 사용)

## 4-4. LLM이 필요한 부분 — 1회 호출 안에서 함께

Business Analyzer와 **같은 호출**에서 다음을 받는다 (별도 호출 아님).

```jsonc
"gapHints": [
  { "slot": "classPrice",    "why": "수강료가 없으면 매출과 손익분기를 계산할 수 없습니다" },
  { "slot": "seatsPerClass", "why": "회당 정원이 매출 상한을 결정합니다" },
  { "slot": "venueCost",     "why": "공간 비용이 고정비의 대부분입니다" }
]
```

`why`는 §5의 질문 카드에서 **"왜 묻는지"** 한 줄로 그대로 보여준다 — 답변률을 올리는 장치다.

## 4-5. 예시 결과 (강아지 클래스)

| 이미 아는 것 | 출처 |
|---|---|
| 사업 형태 = 클래스 | `confirmed` (사용자 문장) |
| 타깃 = 반려견 보호자 | `inferred` → 확인 필요 |
| 홍보 = 인스타·유튜브 | `confirmed` |
| 상품 = 원데이 클래스 | `confirmed` |

| 부족한 것 | 등급 |
|---|---|
| 1인 수강료 | blocking |
| 회당 정원 | blocking |
| 월 수업 횟수 | blocking |
| 1인당 재료비 | blocking |
| 공간 운영 방식·비용 | blocking |
| 대표자의 관련 경험 | important |
| 지역 | important |

→ **7개만 물어본다.** 137개를 처음부터 보여주지 않는다.

# 5. Dynamic Question Generator 설계

## 5-1. 한 라운드 3~5개가 적절한가 — 검토 결과

**적절하다. 근거:**

- 현재 `SectionWizard`가 이미 **질문 그룹 단위 스테핑**을 한다(`gi`/`stepIndex`, "다음/이전", 하단 게이지). 그룹 평균이 **2~4개**라 3~5개는 기존 화면 리듬과 같다.
- 답변 1라운드마다 재분석하면 비용이 는다(§13). 3~5개씩 **최대 3라운드 = 9~15개**가 상한으로 적당하다.
- 5개를 넘으면 "설문지" 느낌이 돌아온다.

**제안**: 라운드당 **최대 4개**, blocking 우선, 같은 주제끼리 묶어서.

## 5-2. 질문 문장 규칙

| 금지 | 대신 |
|---|---|
| "핵심 KPI 및 Unit Economics를 입력해주세요" | "한 번 수업할 때 최대 몇 명까지 받을 생각인가요?" |
| "가동률을 입력하세요" | "정원이 다 차지 않는 날도 있죠. 보통 몇 명쯤 오실 것 같나요?" |
| "CAC를 산정하셨나요?" | "고객 한 명을 데려오는 데 광고비가 얼마나 들 것 같나요?" |

원칙: **초등학교 6학년이 읽고 답할 수 있는 문장.** 전문용어는 괄호로만.

## 5-3. 답변 형식 — "아직 모르겠어요"를 1급 답변으로

```jsonc
{
  "id": "classPrice",
  "q": "1인 수강료는 얼마 정도로 생각하고 계세요?",
  "why": "수강료가 있어야 매출과 손익분기를 계산할 수 있어요",
  "input": {
    "kind": "single",
    "options": ["3만원대", "5만원대", "7만원대", "10만원 이상"],
    "allowCustom": true,           // 직접 입력
    "allowUnknown": true           // 아직 모르겠어요
  },
  "unknownBehavior": "assumption"  // 모른다고 하면 → 가정으로 표시, 숫자 확정 금지
}
```

`아직 모르겠어요`를 고르면:

1. 값은 `unknown`으로 남는다. **AI가 숫자를 대신 정하지 않는다.**
2. `MasterBusinessContext.unknowns[]`에 쌓인다.
3. 문서 생성 때 기존 리얼리티 게이트가 그대로 처리 — **"추가 정의 필요"** + 확인처 안내.
4. 재무 계산은 그 값 없이 계산 가능한 것만 계산한다(현재 `financials.ts`가 이미 그렇게 동작 — 입력이 없으면 계산하지 않음).

> **선택지 제안 방식**: 선택지 4개는 AI가 만들되 **범위형**으로만 준다("3만원대"). 
> 정확한 숫자를 AI가 제시하면 사용자가 그것을 그대로 고를 위험이 있다.

## 5-4. 기존 `aiSuggest`와의 관계

현재 `/api/plan/suggest`는 **질문 1개에 대한 답안 후보**를 만든다(질문당 1회 호출, 최대 60개 질문에서 발동).
새 구조에서는 **라운드 1회 호출로 4개 질문 + 각 선택지를 한꺼번에** 받는다 → **호출이 오히려 줄어든다**(§13).

`/api/plan/suggest`는 **삭제하지 않는다.** 기존 정적 질문 화면(고급 편집·이어쓰기)에서 계속 쓴다.

# 6. 고정 질문과 AI 질문의 역할 분리 — 4계층

```
┌─ CORE ────────── 코드에 고정. 모든 사업 공통. AI가 만들지 않는다.
│   재무 6숫자 · ask(문서 용도) · horizon · needs_funding · structure
│   → 분류표의 "유지" 36개가 여기 후보
│
├─ CONDITIONAL ─── 코드에 고정. 태그·이전 답변이 맞을 때만.
│   기존 showWhen(30개) + TYPE_ADJUST + 새 태그 조건
│   → 분류표의 "조건부" 37개
│
├─ VERIFY ──────── AI 추론을 사용자가 확정. [맞아요]/[아니에요]
│   → 분류표의 "AI추출→확인" 31개
│
└─ DYNAMIC ─────── AI가 정보 공백을 보고 생성. 라운드당 최대 4개.
    사업모델 고유 지표(가동률·churn·전환율) 등 코드에 없는 것
```

## 6-1. VERIFY UX

```
┌──────────────────────────────────────────┐
│ 이렇게 이해했어요                          │
│                                          │
│ 반려견 보호자를 대상으로, SNS 영상으로 모객해 │
│ 오프라인 원데이 클래스를 운영하는 사업        │
│                                          │
│ 업종   교육·강의        [맞아요] [바꿀래요]  │
│ 고객   반려견 보호자     [맞아요] [바꿀래요]  │
│ 운영   오프라인·예약제   [맞아요] [바꿀래요]  │
│ 유입   인스타·유튜브     [맞아요] [바꿀래요]  │
└──────────────────────────────────────────┘
```

- **[맞아요]** → `inferred` → `confirmed`로 승격. 해당 질문은 다시 묻지 않는다.
- **[바꿀래요]** → 그 자리에서 수정 입력. `confirmed`.
- **아무것도 안 누름** → `inferred`로 남고, 문서에서는 단정적으로 쓰이지 않는다.

이 화면 하나가 **31개 질문을 대체**한다.

## 6-2. 안전장치

- DYNAMIC 질문은 **저장 슬롯이 화이트리스트**여야 한다. AI가 만든 임의 `id`를 그대로 저장하면 데이터가 오염된다.
  → 팩에 정의된 슬롯 id에만 매핑. 매핑 실패한 질문은 **버린다**.
- DYNAMIC은 **재무·법적 사실을 물을 수 없다**(그건 CORE의 몫). 겹치면 CORE가 이긴다.

# 8. 재무 엔진 연결 — `financials.ts`는 건드리지 않는다

## 8-1. 핵심 통찰

현재 엔진은 `단가 × 수량`이다. **모든 사업 모델은 "단가 × 파생 수량"으로 환원할 수 있다.**
따라서 엔진을 고칠 필요가 없고, **앞단에 어댑터**만 두면 된다.

```
팩 슬롯 값  ──[RevenueModelAdapter]──▶  FinancialInputs (기존 타입 그대로)
                                          ↓
                              calculateFinancials()  ← 무수정
```

## 8-2. 어댑터 인터페이스 (초안 — 구현 아님)

```ts
import type { FinancialInputs } from "../financials";   // 기존 타입 재사용

export type RevenueModelId = "unit" | "class" | "subscription" | "commerce" | "commission" | "seat" | "content";

export interface RevenueModelAdapter {
  id: RevenueModelId;
  /** 이 모델이 필요로 하는 슬롯 — Gap Analyzer 가 blocking 판정에 쓴다 */
  requires: string[];
  /** 슬롯 값 → 기존 재무 엔진 입력. 값이 없으면 undefined 로 남겨 계산을 건너뛰게 한다 */
  toFinancialInputs(slots: Record<string, number | undefined>): FinancialInputs;
  /** 문서에 적을 산식 설명 — 가정을 드러내기 위해 */
  explain(slots: Record<string, number | undefined>): string;
}
```

## 8-3. 어댑터 예시

```ts
// 교육·클래스
{
  id: "class",
  requires: ["classPrice", "seatsPerClass", "classesPerMonth", "materialCost"],
  toFinancialInputs: (s) => ({
    unitPrice:         s.classPrice,
    unitVariableCost:  s.materialCost,
    // 월 수강생 수 = 정원 × 월 횟수 × 가동률(기본 100%)
    startingVolume:    num(s.seatsPerClass) * num(s.classesPerMonth) * (pct(s.occupancyRate) ?? 1),
    monthlyFixedCost:  sum(s.venueCost, s.instructorCost),
    initialInvestment: s.setupCost,
    monthlyCapacity:   num(s.seatsPerClass) * num(s.classesPerMonth),   // ← 물리적 상한(기존 기능 재사용)
  }),
  explain: (s) => `월 수강생 = 정원 ${s.seatsPerClass}명 × 월 ${s.classesPerMonth}회 × 가동률 ${s.occupancyRate}% (가정)`,
}

// SaaS
{
  id: "subscription",
  requires: ["arpu", "paidUsers"],
  toFinancialInputs: (s) => ({
    unitPrice: s.arpu, unitVariableCost: s.serverCostPerUser ?? 0,
    startingVolume: s.paidUsers,
    monthlyFixedCost: sum(s.devCost, s.fixedOps),
    // churn 은 성장률에서 차감 — 순증가율로 환산
    monthlyGrowthPct: (s.growthPct ?? 0) - (s.churnPct ?? 0),
  }),
}

// 온라인 쇼핑몰
{
  id: "commerce",
  requires: ["aov", "monthlyVisitors", "conversionRate", "cogs"],
  toFinancialInputs: (s) => ({
    unitPrice: s.aov, unitVariableCost: sum(s.cogs, s.shippingCost),
    startingVolume: num(s.monthlyVisitors) * pct(s.conversionRate),
    monthlyFixedCost: sum(s.fixedOps, s.adBudget),   // ← 광고비를 고정비에 넣어 현재 미반영 문제 해소
  }),
}
```

**부수 효과 2가지**

1. `monthlyCapacity`(물리적 상한) — 이미 있는 기능인데 지금은 정밀 재무 모델에서 자유 서술로만 받는다.
   클래스·좌석형은 **정원 × 횟수**로 자동 계산되므로 무한 성장 곡선이 구조적으로 막힌다.
2. `promo_budget`(광고비) — 현재 물어보고 **계산에 반영 안 됨**. commerce 어댑터가 고정비로 넣으면 해소.

## 8-4. 이번 단계 결정

**`financials.ts`는 한 줄도 고치지 않는다.** 어댑터는 별도 파일이며,
어댑터가 없으면 지금처럼 `collectFinancialInputs()`가 그대로 돈다.

# 9. 공식 시장조사와의 연결

## 9-1. 현재 (2026-08-22 구현 완료)

`lib/plan-builder/market-research.ts`의 `planResearchContext()`가
플랜 답변 → 8필드(`title` `sector` `customer` `problem` `model` `revenue` `region` `archetype`)로 매핑해
`researchOfficialMarketEvidence()`에 넘긴다.

## 9-2. Analyzer가 붙으면 좋아지는 이유

현재 매핑은 **답변이 있어야** 채워진다. 즉 사용자가 `market/segments`·`overview/problem`을 답하기 전에는
`customer`·`problem`이 비어 검색 품질이 낮다. Analyzer는 **첫 입력 직후** 이 값을 채운다.

| 필드 | 현재 | Analyzer 연결 후 |
|---|---|---|
| `sector` | 드롭다운 9종 | primary + **model/op 태그** → "반려동물 + 오프라인 클래스" |
| `customer` | 답변 있어야 | 첫 문장에서 즉시 |
| `problem` | 답변 있어야 | 첫 문장에서 즉시 |
| `model` | `main_offer` 답변 | `solution` + revenueModel |
| `region` | 사업 정보 | 동일 (변화 없음) |
| `archetype` | 업종 9→6 매핑 | 태그 기반으로 더 정확 |

**검색어 품질 예시**

```
현재:   sector="교육·강의" customer="" problem=""
        → "교육 강의 시장 통계" 수준의 일반 검색

연결 후: sector="교육·강의(반려동물·오프라인·클래스)"
        customer="반려견 보호자"
        problem="기념일을 직접 준비하고 싶지만 만드는 법을 모름"
        → "반려동물 양육 가구 수" "반려동물 관련 사업체 수" "펫 관련 소비지출"
          같은 실제로 쓸 수 있는 통계에 도달
```

## 9-3. 기존 구현을 깨뜨리지 않는 연결 방법

`planResearchContext()`에 **우선순위 한 단만 추가**한다.

```ts
// 현재
customer: first(a["market/segments"]?.first_target, a["market/personas"]?.situation, ...)

// 제안 — analysis 를 맨 앞에 끼운다. 없으면 지금 그대로.
customer: first(analysis?.customer?.value, a["market/segments"]?.first_target, ...)
```

- `analysis`가 없는 기존 플랜 → **동작 완전 동일**
- `sector`에 태그를 덧붙일 때도 문자열 결합이라 `researchOfficialMarketEvidence`는 무수정
- **`researchOfficialMarketEvidence`·인용 검증·`MarketEvidence`·저장소는 전혀 손대지 않는다**

## 9-4. 역방향 연결 (선택)

시장근거를 찾은 뒤 `opportunities`(SWOT 기회) 같은 `D 추출` 질문은
**근거를 바탕으로** 제안할 수 있다 → 근거 있는 SWOT. 2차 과제로 둔다.

# 10. MasterBusinessContext

## 10-1. 왜 필요한가

현재는 `plan.answers`(raw 137슬롯)를 섹션마다 잘라 프롬프트에 넣는다. 문제:

- 같은 사실이 4곳에 흩어져 있다(`value_prop`/`purpose`/`uvp`/`differentiator`)
- **출처가 없다** — 사용자가 답한 것인지, AI가 추론한 것인지, 계산 결과인지 구분이 없다
- 섹션 생성기가 매번 raw answers를 해석해야 한다

## 10-2. 구조 (초안)

```ts
export type FieldStatus = "confirmed" | "inferred" | "unknown";
export type FieldSource =
  | "user_input"        // 자유 서술
  | "user_answer"       // 질문 답변
  | "user_verified"     // AI 추론을 사용자가 확인
  | "official_evidence" // MarketEvidence
  | "calculation"       // financials.ts 계산 결과
  | "ai_inference";     // AI 추론 (미확인)

export interface Field<T> {
  value: T | null;
  status: FieldStatus;
  source: FieldSource;
  /** official_evidence 일 때만 — 기관·기준일·원문 */
  citation?: { sourceName: string; observedAt: string; sourceUrl: string };
  /** 어느 질문/문장에서 왔는지 (되짚기용) */
  origin?: string;
}

export interface MasterBusinessContext {
  business:    { name: Field<string>; description: Field<string>; region: Field<string>;
                 stage: Field<string>; primary: Field<string>; tags: Field<string[]> };
  customer:    { segment: Field<string>; persona: Field<string>; budget: Field<string>; channels: Field<string[]> };
  problem:     { statement: Field<string>; frequency: Field<string>; currentAlternative: Field<string> };
  solution:    { statement: Field<string>; differentiator: Field<string> };
  products:    { main: Field<string>; composition: Field<string>; price: Field<number> };
  revenueModel:{ id: Field<RevenueModelId>; streams: Field<string[]>; slots: Record<string, Field<number>> };
  operations:  { delivery: Field<string>; coverage: Field<string>; capacity: Field<number>; who: Field<string[]> };
  marketing:   { channels: Field<string[]>; message: Field<string>; budget: Field<number> };
  competition: { alternatives: Field<string[]>; notes: Field<string>; gap: Field<string> };
  market:      { evidence: MarketEvidence[] };            // ← 그대로 재사용
  team:        { size: Field<number>; roles: Field<string>; hiring: Field<string> };
  traction:    { hasRevenue: Field<boolean>; items: Field<string[]> };
  finance:     { inputs: FinancialInputs; result: FinancialResult | null };  // ← 기존 타입 재사용
  risks:       { constraint: Field<string>; runway: Field<string>; plan: Field<string> };
  assumptions: Array<{ label: string; value: string; basis: string }>;   // 가정으로 쓴 값
  unknowns:    Array<{ slot: string; label: string; grade: "blocking"|"important"|"optional" }>;
}
```

## 10-3. 절대 규칙

```
status === "inferred"  →  본문에 사실로 쓰지 않는다
status === "unknown"   →  "추가 정의 필요" + 확인처 안내 (기존 리얼리티 게이트 그대로)
source === "ai_inference" → 문서에 인용 표기 금지
source === "official_evidence" → 기관명 + 기준일 + 원문 링크 필수 (이미 구현됨)
source === "calculation" → 산식과 가정을 함께 표기 (이미 구현됨)
```

## 10-4. 어디에 끼우나

```
plan.answers (raw)  ──buildMasterContext()──▶  MasterBusinessContext
                                                    │
                             ┌──────────────────────┼──────────────────────┐
                             ▼                      ▼                      ▼
                    section-generator 프롬프트   재무 어댑터         시장조사 context
                    (evidence·conflicts 옆에)   (§8)                (§9)
```

`SectionGenInput`에 `context?: MasterBusinessContext` 한 필드를 더하는 형태 —
**`evidence`·`conflicts`를 넣었던 것과 완전히 같은 패턴**이다. 없으면 지금 그대로 동작한다.

```
  "조금만 더 알려주세요. 숫자가 있어야 손익을 계산할 수 있어요."

STEP 4  ─ 2라운드 (최대 4개, 필요할 때만)
        ↓
STEP 5  ─ "사업 구조가 거의 완성됐어요"  충족률 92%
  [ 공식 시장자료 찾아보기 ]  ← 기존 기능 (이미 구현됨)
        ↓
STEP 6  ─ 재무 확인  ← 기존 FinancialReview 화면 재사용
  "이렇게 계산했어요. 숫자가 이상하면 고쳐주세요."
        ↓
STEP 7  ─ [ 사업계획서 만들기 ]
        ↓  기존 생성 파이프라인 그대로 (25섹션 · 큐 · 스트리밍)
```

|---|---:|---:|

- **Gap Analyzer는 규칙 기반** — LLM 호출 없음
- **Analyzer + Gap을 한 호출**로 (프롬프트 하나, 출력 하나)
- **프롬프트 캐시**: Analyzer 시스템 프롬프트(태그 사전·팩 목록)는 고정 → `cache: true` 적용 대상

- **재분석 트리거 제한**: 답변이 바뀌어도 라운드가 끝날 때만 재분석
- **rate limit**: 기존 `enforceRateLimit` 패턴으로 `plan-analyze` 20회/10분

Analyzer 실패 → **기존 137개 위저드로 그대로 진입**. 기능이 사라지지 않는다.

# 15. 최종 보고서

## A. 현재 질문 시스템의 문제점

1. **순서가 고정이다** — 25섹션 × 평균 5문항을 1.1부터 순서대로 만난다. 내 사업과 무관한 질문(지식재산·출구 전략)도 같은 무게로 나온다.
2. **업종 차별화가 0이다** — 카페와 SaaS가 같은 137문항을 받는다. 사업모델 고유 지표(가동률·churn·전환율)를 물을 방법이 아예 없다.
3. **중복이 구조적이다** — 같은 사실을 최대 4번 묻는다(`value_prop`/`purpose`/`uvp`/`differentiator`). 그중 3쌍은 `consistency.ts`가 **충돌로 잡아야 할 만큼** 자주 어긋난다.
4. **AI가 이미 아는 것을 묻는다** — 사업 설명에 다 있는 내용(고객·문제·해결·상품)을 36개 질문으로 다시 묻는다.
5. **재무 모델이 하나다** — `단가 × 수량`뿐이라 클래스·구독·쇼핑몰의 실제 구조를 담지 못한다.
6. **시장 규모를 사용자에게 떠넘겼다** — `market_size` 자유 서술. 이제 공식 검색이 있으므로 불필요.
7. **`aiSuggest` 비용이 예측 불가** — 질문당 1회 호출 × 60개 질문.
8. **첫 화면의 벽** — "1.1 한눈에 보기"에 12개 질문이 있고 그중 4개가 분기 질문이다. 이탈 지점.

## F. Dynamic Question Schema

```ts
export interface DynamicQuestion {
  /** 반드시 팩 슬롯 id 와 일치해야 저장된다 (화이트리스트) */
  id: string;
  q: string;                 // 쉬운 한국어 한 문장
  why: string;               // "왜 묻는지" 한 줄 (≤ 40자)
  input:
    | { kind: "single"; options: string[]; allowCustom: boolean; allowUnknown: boolean }
    | { kind: "multi";  options: string[]; max?: number; allowUnknown: boolean }
    | { kind: "number"; unit: string; hint?: string; allowUnknown: boolean }
    | { kind: "text";   placeholder?: string; allowUnknown: boolean };
  grade: "blocking" | "important" | "optional";
  /** 답이 기존 질문 슬롯에도 기록되면 여기에 (하위 호환의 핵심) */
  mapsTo?: { sectionKey: string; qid: string };
}

export interface QuestionRound {
  round: 1 | 2 | 3;
  intro: string;                 // "숫자가 있어야 손익을 계산할 수 있어요"
  questions: DynamicQuestion[];  // 최대 4
  completeness: number;          // 0~100
  canFinish: boolean;            // 종료 조건 충족 여부
}
```

### 저장 — **DB 마이그레이션 불필요**

`normalizeState()`가 plan 객체를 명시적으로 재조립하므로 **새 최상위 필드는 떨어진다**.
따라서 분석 결과는 **`plan.answers["__analysis"]` 가상 섹션 키**에 저장한다.

- `answers`는 `Record<string, Record<string, unknown>>`로 **키 검사 없이 통과**한다(`plan-server-store.ts:81`)
- 진행률은 `blueprint` 기준으로만 세므로 **영향 없음**(`PlanOverview.tsx:138-147`)
- **선례가 이미 있다**: `FINANCIAL_OVERRIDE_KEY = "financials/__review"`
- 답변 이어받기(`createPlan({inheritAnswers})`)에 자동 포함되는 부수 효과 — 같은 사업의 두 번째 문서는 분석을 다시 하지 않아도 된다

## N. 기존 시스템을 깨뜨리지 않는 최소 변경 전략

### 원칙 5가지

1. **가산만 한다(additive-only)** — 새 필드는 전부 `optional`. 없으면 현행과 **바이트 단위로 동일**하게 동작.
   (`evidence`·`conflicts`를 넣을 때 검증된 방식)
2. **같은 저장소를 쓴다** — 동적 답변도 `plan.answers[sectionKey][qid]`. 그래야
   `financials.ts`·`consistency.ts`·`section-generator.ts`가 **아무것도 모른 채** 그대로 동작.
3. **가상 섹션 키로 저장** — `plan.answers["__analysis"]`. DB 마이그레이션 0, 진행률 영향 0.
4. **두 경로 공존** — 동적(빠른 길) / 위저드(정밀한 길). 사용자가 언제든 갈아탄다.
5. **실패는 현행으로 떨어진다** — Analyzer 실패·키 없음·JSON 깨짐 → 기존 137개 위저드.

### 회귀 방지 체크리스트

| 확인 | 방법 |
|---|---|
| 분석 없는 기존 플랜이 동일하게 생성되는가 | `buildUserPrompt`에 context 없을 때 문자열 동일 (기존 테스트 D 패턴) |
| 재무 계산이 안 바뀌는가 | `collectFinancialInputs` → `calculateFinancials` 결과 스냅샷 비교 |
| 정합성 검사 15종이 그대로 도는가 | `findConsistencyIssues` 기존 테스트 |
| 위저드 진입이 안 깨지는가 | `/plan/{ch}/{sec}` 스모크 |
| `/plan/start`를 건너뛸 수 있는가 | 자유 입력 비우고 진행 → 현행 흐름 |
| 시장조사가 그대로 도는가 | `planResearchContext` 기존 테스트 (analysis 없을 때) |
| 답변 이어받기가 깨지지 않는가 | `__analysis` 포함 복사 확인 |

### 롤백

동적 경로는 **기능 플래그 하나**(`PLAN_DYNAMIC_QUESTIONS`)로 껐다 켤 수 있게 한다.
끄면 `/plan/start`가 현행 2단계로 돌아가고, 저장된 `__analysis`는 그냥 읽히지 않는다.
