# newapp 계정 연결과 홈페이지 공개·복원 검증

## 결론

사용자가 승인한 출시 전 `newapp` (`hagzlppubxxzxllsehbr`)에 누락된 **0027~0030을 반영했다**. 외부 DB·서비스 통합 검사 **16/16**, 임시 로컬 앱의 실제 이메일 로그인·HTTP 검사 **8/8**, 외부 호출을 차단한 회귀 **46/46**이 통과했다.

이 결과는 Google OAuth, PG 결제, Cloudflare 배포·Workflow의 통과가 아니다. 정식 출시 판정은 계속 `false`다. 원래 개발 서버와 `.env.local`, 운영 Worker 설정은 변경하지 않았다. `PLAN_ACCOUNT_LINKING_ENABLED=true`와 홈페이지 편집 미리보기 권한은 검증 프로세스에만 적용했다.

- 전후 증거: `artifacts/prelaunch-migration/2026-09-15T02-07-00.973Z/`. `before.json`에는 관련 스키마·이력·홈페이지/버전 백업과 계획/프로젝트/사용량 지문이 있다. **전체 DB 백업은 아니다**.
- 이 폴더는 Git 제외이며 디렉터리 0700, 파일 0600으로 저장했다. 비밀키는 저장하지 않는다. 재실행은 이력을 먼저 읽고 이미 적용된 변경을 다시 쓰지 않는다.

## 브라우저와 HTTP 검증

실제 소스를 `/private/tmp/oneul-prelaunch-browser-*`로 복사해 임시 loopback 포트에서 실행했다. 원본 환경 파일·배포 설정·AI/PG 키는 복사하지 않았다. 원격 DB는 승인된 `newapp`이고 앱만 로컬 격리다. 기존 8083/8094 서버는 변경하지 않았다.

1. 실제 `/api/plan/state`로 비회원 사업을 저장했다.
2. 브라우저의 이메일 로그인 화면을 조작해 같은 사업 이전과 HttpOnly 로그인 쿠키를 확인했다.
3. 이전 비회원 쿠키를 가진 다른 브라우저는 자료를 읽을 수 없고 오래된 저장은 409로 거절됐다.
4. 같은 계획에서 홈페이지 생성 요청을 반복해도 프로젝트와 홈페이지 ID가 유지됐다.
5. 버전 정보 없는 공개 요청은 428, 정상 공개 후 URL에는 저장한 공개본이 표시됐다.
6. 비공개 수정 후 기존 URL은 이전 내용 유지, 새 주소는 오류 화면과 `noindex`, 원문 응답에 비공개 문구 없음, 문의 API는 404였다. 오래된 공개 요청은 409로 거절됐다.
7. 실제 공개·복원 HTTP 경로를 거쳐 원래 내용·주소·과거 버전 이력이 유지됐다.
8. 로그아웃 상태의 편집 API는 거절됐고 재로그인 뒤 같은 홈페이지와 공개 버전을 다시 읽었다.

첫 실행 `155b487d5504fafa`는 비공개 URL을 HTTP 404로만 판단한 테스트가 실패했다. Next.js는 스트리밍된 `notFound()`에서 HTTP 200을 반환할 수 있으므로, **상태 코드를 무조건 허용하지 않고 오류 화면·noindex·비공개 원문 미노출·공개 API 거부까지 함께 검사**하도록 수정했다. [Next.js not-found 공식 문서](https://nextjs.org/docs/app/api-reference/file-conventions/not-found)

후속 실행 `49b28d98535cad2c`는 8/8 통과했으며 응답 증거를 보관했다. 이메일 로그인 UI와 쿠키, 자료 이전은 실제 동작이고 홈페이지 수정·공개·복원은 브라우저 세션의 HTTP API로 검사했다. 홈페이지 편집 버튼을 모두 클릭한 UI 전체 검사는 아니다. 홈페이지 편집 권한은 임시 앱에서 가상 이메일 1개에만 허용한 미리보기 권한으로, 결제 통과로 계산하지 않는다.

최종 실행 **`04d579f2cc42cb9d`도 8/8 통과**했다. 로그인·재로그인 뒤 로딩 화면을 지나 실제 사업 제목이 목록에 표시되는 것을 추가 확인했다. `artifacts/prelaunch-browser/04d579f2cc42cb9d/`에 `report.json`, `signed-in-plan.png`, `reconnected-plan.png`, 비공개 URL의 HTML·404 화면 증거와 정리 확인 결과를 보관했다. 페이지 JavaScript 오류는 0건이며 TypeScript와 `git diff --check`도 통과했다.

## 안전장치와 남은 범위

- DB 테스트 스크립트는 정확한 `newapp` 주소와 명시적 실행 플래그를 요구하며 실행별 소유자·계정·프로젝트·홈페이지 범위만 허용한다.
- 테스트 홈페이지는 모두 다시 비공개 처리한다. 가상 계정과 관련 자료는 추적 가능하도록 보관하며 비밀번호·세션은 결과 파일에 남기지 않는다.
- 이번 단계에서 가상 계정 5개와 홈페이지 4개를 만들었다. 첫 브라우저 실패 및 후속 두 실행의 자료도 포함한다. 마지막 읽기 전용 조회에서 4개 모두 `status=draft`, `published_slug=null`임을 확인했다. 임시 앱 3개도 모두 종료했다. 런타임 경로 미지정으로 시작 전에 중단된 1회는 계정이나 서버를 만들지 않았다.
- 유료 AI 호출 0회, 실제 결제 0회, 기존 AI 예산 장부 변경 없음. 공개 Worker 배포·요금제 변경·커밋·푸시 없음.
- 기존 localhost 검사 및 스테이징 배포 보호 정책은 완화하지 않았다.
- 0029의 DB 반영과 함수 접근 권한은 확인했지만 실제 장애 알림 수신이나 서비스 전체 비용 차단까지 검증한 것은 아니다.

다음 순서는 보호된 테스트 앱의 설정 확정 → Google 로그인/콜백 → PG sandbox 승인·실패·취소·중복·환불 → Cloudflare Workflow 생성·재시작·재접속 다운로드 → 알림 수신·비용 제한·복구 절차다. 원격 앱에서 계정 연결을 켤 때는 검증에 사용한 소유권 HMAC 비밀값을 임의 변경하지 말고, 환경별 키 일치와 마이그레이션 적용 여부를 먼저 확인한다.
