# 범용 사업 진단과 통합 채팅 구현 계획

작성: 2026-09-16. 상태: 0~1단계 로컬 구현·검증 완료, 2~5단계 미완료. 최신 증거와 한계는 10절 참고.

## 1. 제품 결정

목표는 모든 사업의 정답을 미리 보유하는 것이 아니라, 알려진 업종과 미분류·복합·새로운 사업을 모두 입력하고 구체화할 수 있게 하는 것이다. 새로운 사업의 성공, 수요, 기술 가능성, 법적 적합성을 자동으로 보증하지 않는다.

화면은 하나의 채팅이다. 세 시작 카드가 대화의 목적과 질문 순서를 정하고, 같은 대화 안에서 선택과 직접 입력, 필요한 상담을 이어간다. 하단 입력창은 항상 유지한다. 질문 답변/자유 메모/AI 도움 모드를 사용자가 매번 고르는 화면은 기본 경험에서 없앤다.

내부에서는 결정론적 질문·저장·계산과 AI 해석·상담을 분리한다. 선택지를 누르거나 직접 답한다고 매번 AI를 호출하지 않는다. 모호한 입력을 억지로 답변으로 저장하거나 무조건 AI로 보내지도 않는다.

기존 `intake-two-path-plan-2026-09-16.md`의 별도 자유 대화 경로, 안내 모드 입력창 기본 접힘은 이 계획으로 대체한다. 그 문서의 비용·소유권·중복 방지 원칙은 유지한다. `intake-select-first-spec-2026-09-16.md`의 선택형 컨트롤은 재사용하되 모든 정보를 선택지만으로 표현하도록 강제하지 않는다. 두 문서의 제안 한도를 현재 승인된 운영 한도로 간주하지 않는다.

## 2. 현재 코드에서 확인한 출발점

- `BusinessIntake.tsx`에 저장·재접속·409 충돌·소유자 분리·고정 입력창·말풍선 전환이 있다.
- `intake-core.ts`, `intake-questions.ts`는 세 시작 유형과 핵심 질문 11개, 11업종의 선택 상세 질문 4개를 제공한다.
- 미커밋 `intake-options.ts` 및 선택형 UI는 고객·상품·채널 칩, 수량 스테퍼, 금액 범위, 기간 프리셋을 제공한다. 버리지 않고 회귀 검사 후 통합한다.
- `typedEntryCommand`는 첫 자유 입력을 대부분 사업 소개로 바로 저장한다. 질문과 복합 입력을 오인하지 않도록 교체할 지점이다.
- 현재 자유 메모는 `message` 저장 후 조건에 따라 `extract`를 예약한다. 모든 복합 입력이 즉시 유료 작업으로 이어지지 않도록 예약 정책을 변경한다.
- `helpIntake`는 진단 항목 안내용이며 일반 사업 상담·아이디어 구체화의 완성된 엔진이 아니다. 이름만 바꿔 자유 상담이 구현됐다고 처리하지 않는다.
- 업종 해석이 `model.ts`와 신규 `intake-sector.ts`에 중복돼 있다. 서버/클라이언트가 같은 규칙을 쓰게 합친다.
- 계획 당시 첨부 화면은 `127.0.0.1:8103`의 기존 채팅 컴포넌트이며 JSON 응답 오류가 보였다. 이후 8103이 예전 결제 미리보기 사본이고 영구 저장소 없이 운영 모드로 실행돼 빈 500 응답을 반환함을 확인했다. 기존 격리 서버 `61726`과 다른 실행 사본이다.

## 3. 업종 목록 대신 공통 사업 구조

### 공통 정보

기존 사업정보를 기준 데이터로 유지하고 다음 내용을 단계별로 모은다. 아래 목록 전체를 새 질문으로 추가하지 않는다. 기존 답변에서 얻은 내용은 다시 묻지 않으며 필요한 구조 질문만 핵심 질문 예산 안에서 선택한다.

| 구조 | 저장할 내용 | 예시 |
| --- | --- | --- |
| 사업 단계 | 탐색/기획/운영, 현재 개선 목표 | 첫 고객 찾기, 재구매 개선 |
| 고객과 지불자 | 누가 쓰고 누가 비용을 내는가 | 개인, 기업, 이용자와 구매자가 다름 |
| 해결할 문제 | 현재 불편, 대안, 아직 확인 안 된 가설 | 대기 시간, 반복 업무, 수요 미확인 |
| 제공하는 것 | 실물/수행 서비스/소프트웨어/공간/콘텐츠/복합/직접 설명 | 센서 대여와 돌봄 서비스 결합 |

| 자원과 숫자 | 예산, 시간, 인력, 비용, 처리량, 측정 기간 | 기간별 매출과 월 고정비 구분 |
| 증거와 다음 행동 | 사용자 확인 사실, 가설, 실험, 다음 확인 지표 | 잠재 고객 인터뷰, 시제품 시험 |

`sector` 11종은 표시·예시·기존 PPT 판형 호환을 위해 남긴다. 질문 진행이나 생성 가능 여부를 결정하는 필수 관문에서는 제외한다. 미분류와 복합도 정상 경로이며 `general`로 강제 축약해 원문을 잃지 않는다.

구조의 미확정 추론은 추천일 뿐이다. 사용자가 선택한 사업 형태가 키워드 추정보다 우선한다. 단일 업종 키워드가 가격 단위나 수익 방식을 확정해서는 안 된다.

### 세 시작 유형

| 시작 | 우선 질문 | 첫 결과 |
| --- | --- | --- |
| 아이디어 없음 | 경험·관심·시간·예산, 제공 방식 선호 | 조건에 따른 탐색 후보와 맞지 않는 조건 |
| 사업 구상 있음 | 설명·고객·문제·제공 가치·수익·운영 조건 | 입력 기반 사업 요약과 최소 실행안 |
| 운영 중 | 현재 상품·고객·문제·기간별 실적·운영 제약·목표 | 변화, 원인 가설, 개선 행동, 확인 지표 |

아이디어 없음의 무과금 후보는 기존의 한정된 카탈로그와 명시적인 조합 규칙이다. '세상에 없던 아이디어를 무과금으로 무한 생성'한다고 약속하지 않는다. 새로운 조합을 요청하면 AI 제안 1회 또는 사용자가 직접 설명하는 경로를 제공한다. 제안은 사용자 사실과 분리해 보관한다.

### 질문 선택 규칙

1. 확정된 값, 미정으로 답한 값, 관련 없는 항목은 건너뛴다.
2. 현재 단계의 핵심 빈칸과 계산·다음 행동에 필요한 선행 항목을 우선한다.
3. 질문은 안정적인 ID, 적용 조건, 답변 스키마, 선택지 생성 규칙, 생략 조건을 갖는다. AI는 질문 ID나 다음 단계의 권한을 갖지 않는다.
4. 구독이면 갱신 주기, 현장 서비스면 범위·처리 시간, 생산이면 수량·납기, 공간이면 수용량·시간 단위 등 구조별 보충 질문을 조합한다.
5. 공통 핵심은 보통 8~12개 사용자 응답 턴, 상세는 선택적으로 최대 4개다. 카드 안 여러 필수 단계를 숨겨 질문 수를 줄인 것처럼 계산하지 않는다. 예산을 넘는 확인은 미정/나중에 확인으로 남긴다.
6. 선택지는 현재 사업 원문과 선택한 구조를 우선하고 업종 카탈로그는 예시로 사용한다. `직접 답하기`, `여기에 없어요`, `아직 미정`을 항상 제공한다.

## 4. 한 채팅의 입력 처리

| 입력 상황 | 처리 | 외부 AI |
| --- | --- | --- |
| 선택지, 날짜, 숫자와 단위 | 스키마 확인 후 해당 질문에 저장 | 0회 |
| 현재 고객 질문에 '근처 직장인' | 질문 ID와 원문을 연결해 저장 | 0회 |
| '예산: 100만원'처럼 명확한 항목 지정 | 규칙으로 후보 생성, 변경 대상 확인 | 0회 |
| '대학생과 직장인 중 누구부터 공략할까요?' | 원문 저장 후 상담 요청으로 표시, 제한된 상담 작업 | 최대 1회 |
| '서울에서 100만원으로 카페와 강의를 같이...' | 원문 저장, 여러 항목의 정리 후보 표시 | 정리 요청/확인 시 최대 1회 |
| 답변인지 상담인지 불명확 | 같은 스레드에 `이 질문의 답변` / `상담하기` 확인 | 확인 전 0회 |
| 인사, 확인, 지원하지 않는 요청 | 짧은 정해진 응답 또는 필요한 입력 확인 | 0회 |

라우팅을 위해 별도 AI 분류 호출을 추가하지 않는다. 선택 이벤트의 질문 ID가 가장 확실한 신호이며, 자유 문장은 숫자·명시적 라벨·질문 표현 등 보수적인 규칙만 쓴다. 물음표 하나나 짧은 정규식만으로 모든 문장의 의도를 확정하지 않는다.

첫 문장은 카드 선택 없이 보낼 수 있다. 우선 원문을 보존하고, 시작 유형이 불명확하면 세 카드를 같은 대화 안에서 확인한다. '카페가 괜찮을까요?'를 사업명으로 확정하거나 '예전에 운영했다'를 현재 운영 중으로 확정하지 않는다. 상담만 원하면 유형 확인을 미룰 수 있지만 맞춤 사업안/문서 생성 전에는 확인한다.

사용자 말풍선은 즉시 나타나고 저장 중/저장 실패를 구분한다. 기존 짧은 질문 전환 연출을 유지하되 이를 AI가 생각 중이라고 표시하지 않는다. 실제 AI 대기는 별도 상태로 표시한다. AI 대기 중에도 직접 답변은 가능하며 추가 상담은 대기 메모로 보존하고 자동으로 무한 실행하지 않는다.

상담 답변 후 원래 질문으로 자연스럽게 돌아오며 이미 확정된 정보는 다시 묻지 않는다. 제안된 답변의 채택도 명시적으로 확인한다. 하단 입력창과 미전송 초안은 모든 전환에서 보존한다.

## 5. AI 사용 위치와 상한

### 호출 정책

- 기본 진단, 기본 요약, 기본 후보, 계산: 0회.
- 사용자가 요청한 상담 또는 복합 입력 정리: 요청당 외부 호출 최대 1회. 해석 -> 답변 -> 사업안 생성의 연쇄 호출은 하지 않는다.
- 상담 응답에 사용자 입력에서 얻은 후보가 필요하면 같은 구조화 응답에 포함한다. 답변 텍스트와 후보는 별도로 검증한다. 모델의 답변 자체를 원문 근거로 사용하지 않는다.
- 짧은 해석/상담은 기존 20초 제한을 유지하고 초기 출력 상한은 합계 1,200토큰으로 둔다. 후보 수·최근 대화·입력 길이도 제한한다. 잘못된 JSON을 고치기 위한 재호출, 자동 재시도, 제공자 폴백은 하지 않는다.
- 새 사업 아이디어/맞춤 사업안 생성은 별도의 명시적 요청과 작업별 비용 예약으로 처리한다. 긴 문서/PPT 생성의 기존 단계별 상한은 별개로 유지하며 '진단 한 번당 1회'에 숨기지 않는다.
- 즉시 AI 응답이 꼭 필요하지 않은 메모는 저장만 한다. 사용자가 모아서 정리하도록 하며 키 입력/선택마다 호출하지 않는다.

### 비용 통제

사업별 동시 AI 작업 1개, 동일 요청 ID/사업 버전의 결과 재사용, 확인되지 않은 전송의 재시도 보호를 유지한다. 다른 사용자의 원문/개인화 응답을 공유 캐시로 재사용하지 않는다.

실행 전 신원별·사업별·전역 한도와 최대 입력/출력 토큰 기반 비용을 영구 저장소에서 원자적으로 예약한다. 카운터 확인 실패는 유료 실행을 중단하되 진단은 유지한다. 완료된 요청/409/중복 클릭이 다시 AI를 호출하지 않아야 한다. 실패했다고 비용이 없다고 가정하지 않는다.

운영에서는 서버 측 킬 스위치와 명시적인 모델 설정을 둔다. 미설정이면 상담만 비활성화한다. 일일 횟수/금액 상한은 운영 모델과 실측 사용량, 별도 운영 예산에 맞춰 정하며 구현자가 임의로 무제한 또는 '정해진 예산이면 모든 사용자를 수용'으로 약속하지 않는다.

현재 합성 검증 장부의 마지막 확인값은 승인 $30, 예약 $18.99255, 남은 예약 $11.00745다. 이는 운영 예산이 아니고 이번 계획의 신규 승인도 아니다. 실제 호출 전 장부와 실행별 상한을 재확인한다. 계획 작성에서는 유료 호출을 하지 않는다.

## 6. 저장과 결과물 연결

### 호환 원칙

새 사업정보 저장소를 따로 만들지 않는다. 기존 `CoachState.fields`, 사업 answers, `__business_intake`에 역할에 맞게 확장한다.

- 기존 business/customer/problem/offer/channel/price 등 확정 필드는 유지한다.
- 사업 구조 추가 항목은 기존 사업 answers에 안정적인 항목 ID로 저장하고, 질문 상태/추론 후보는 intake 메타데이터에 둔다. 같은 사실의 독립적인 두 '최종 값'을 만들지 않는다.
- 원문 메시지 ID, 근거 구절, 확정 여부, 출처, 단위, 기간, 항목별 수정 버전을 함께 유지한다. UI 선택지 라벨만으로 데이터를 식별하지 않는다.
- 공통 정보를 바꾸지 않는 대화·후보·로딩 변경은 문서 근거 버전을 올리지 않는다. 확정한 구조 정보가 결과물에 쓰이면 기존 source projection/dependency 목록에 포함한다.
- 현재 intake state v1을 읽는 호환 경로를 유지하고 새 쓰기는 명시적인 v2 마이그레이션을 거친다. 질문팩 버전도 분리한다. 기존 답변을 자동으로 재분류하거나 삭제하지 않는다. 오래된 탭의 쓰기는 호환 처리하거나 409/갱신 안내로 차단한다.
- API는 `/api/plan/chat`을 확장한다. 기존 명령은 유지하고 통합 입력의 원문 저장/의도 확인/상담 작업을 명시적인 명령으로 추가한다. 상담 접수와 작업 생성은 한 번의 저장 트랜잭션 및 영수증으로 묶는다.
- 기존 `extract/help/design` 중 짧은 해석/상담은 공통 실행기를 쓰되 마이그레이션 중 이전 실행 결과가 새 상태를 덮어쓰지 못하게 한다. 새 장기 작업 시스템을 별도로 만들지 않는다.

### 숫자와 미지의 사업

금액 범위를 골랐다고 하한/상한/중간값을 실제 단가로 자동 저장하지 않는다. 범위는 범위, 미정은 미정이다. 정확값을 선택했을 때만 확정된 단일 수치로 계산한다. 표현에 원/건, 원/월, 원/시간과 적용 상품·기간을 함께 보존한다.

서로 다른 수익원이나 단위는 각각의 항목 ID로 구분한다. 단위·기간이 호환되지 않는 값은 합산하거나 손익분기를 계산하지 않는다. 초기 버전은 계산 보류 사유를 보여주고, 검증된 계산만 제공한다. 복합 사업을 하나의 평균 가격으로 임의 축약하지 않는다.

검증되지 않은 새 사업은 계획서에서 '시장 검증/기술 검증이 필요한 가설'로 표현한다. 존재하지 않는 실적·시장규모·사례·사진을 채우지 않는다. 홈페이지 미리보기와 PPT도 확정 정보와 준비 현황을 사용한다. 알려진 업종 판형이 안 맞으면 공통 판형 + 해당 사업 구조 모듈을 쓴다.

변경 반영은 기존 `/api/plan/artifact-updates` 승인 경로를 사용한다. 수동 문구/이미지/배치와 공개 홈페이지는 자동 덮어쓰기 금지다. 기존 문서가 있으면 새 초안 실패 시 보존한다.

## 10. 0~1단계 구현 결과

### 실제 반영

- 하나의 하단 입력창을 유지하고 질문 답변/자유 메모/AI 도움 상시 모드 탭을 제거했다. 기존 칩·수량·금액·기간 컨트롤은 유지한다.
