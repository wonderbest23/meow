## 2. mapsTo 의미 오류 수정 (§2 요구)

| 슬롯 | 1차 | 2차 | 이유 |
|---|---|---|---|
| `venueCost` | → `fixed_total` 직접 | `contributesTo: fixed` · `__analysis.slots` 에 원본 유지 | 공간비는 고정비의 한 항목. 광고비·통신비가 더 있을 수 있다 |
| `materialCost` | → `variable_per_unit` 직접 | `contributesTo: variable` | 재료비 외 결제수수료·포장·배송이 붙는다 |
| `cogs`(commerce) | → `variable_per_unit` 직접 | `contributesTo: variable` | 질문이 "원가+포장·배송"이라 수수료가 빠진다 |
| `fixedOps`·`fixedTotal`·`unitCost` | 합계를 직접 묻는 질문 | 유지 | 질문 자체가 합계 |

**숫자 확인 화면 (실측)**
```
월 판매(수강) 건수      48 건/월     정원 6명 × 월 8회 = 약 48명
1건당 변동비 합계       15,000 원/건  1인당 재료비 15,000원
  "재료비 외에 결제 수수료·포장비·배송비·플랫폼 수수료처럼 … 있으면 더해서 적어주세요."
[이 숫자로 할게요 →]   [건너뛰기 — 나중에 직접 입력]
```
실측: 변동비 칸을 15,000 → 18,000 으로 고치고 확인 → `variable_per_unit: "18,000원"` 저장. 구성 항목 값은 `__analysis.slots.materialCost` 에 그대로.
위저드에 이미 `fixed_total`/`variable_per_unit` 이 있으면 카드도 생기지 않고 구성 항목 질문도 나오지 않는다(테스트 A).
`financials.ts` 는 여전히 합계 칸만 읽는다 — 무수정.

## 3. PlanBusinessContext 실제 Schema (`context/build.ts`)

```ts
type ContextSource = "user_input" | "user_answer" | "ai_inference" | "official_evidence" | "calculation";
interface ContextField<T> { value: T | null; status: "confirmed" | "inferred" | "unknown"; source: ContextSource }

interface PlanBusinessContext {
  identity:       { name, industry, stage, region, description }
  classification: { primary, modelTags: string[], operationTags: string[] }
  customer:       { target, persona, budget, channels: string[] }
  problem:        { statement, frequency, currentAlternative }
  solution:       { mainOffer, description, differentiator }
  revenue:        { model, streams: string[], unitPrice, volume }
  operations:     { delivery, coverage, venueType, capacity, who: string[] }
  marketing:      { channels: string[], acquisitionModel: string[], message, budget }
  competition:    { alternatives: string[], knownCompetitors, differentiator }
  traction:       { established, hasRevenue, items: string[] }
  team:           { size, ownerExperience }
  funding:        { needs, amount, use }
  goals:          { horizon, main: string[], constraint }
  finance:        { summary?: string }                       // financialsToReference() 결과
  unknowns:       Array<{ field, label }>
  conflicts:      Array<{ title, detail }>                   // 위저드 ≠ VERIFY
}
```
(모든 리프는 `ContextField<…>`. 설계안의 `evidenceSummary` 는 넣지 않았다 — §8 참조.)

## 4. Context 구성 우선순위 (`pick()` — 위가 이김)

| 순위 | 출처 | source | status | 예 |
|---|---|---|---|---|
| 1 | 위저드 직접 입력 `plan.answers[섹션][qid]` | `user_answer` | confirmed | `market/segments.first_target` |
| 2 | 동적 질문 답 `__analysis.slots[id]` (confirmed) | `user_answer` | confirmed | `venueType`, `differentiator` |
| 3 | VERIFY 로 확인한 Analyzer 값 | `user_answer` | confirmed | `analysis.customer(confirmed)` |
| 4 | 시스템 계산 `calculateFinancials()` | `calculation` | confirmed | `finance.summary` |
| 5 | 공식 MarketEvidence | `official_evidence` | — | **context 에 넣지 않음** (근거 블록이 따로 감, §8) |
| 6 | 사용자가 확인하지 않은 Analyzer 값 | `ai_inference` | **inferred** | `analysis.deliveryModel(inferred)` |
| 7 | 없음 | — | unknown | → `unknowns[]` |

사업 정보(`business.*`)는 `user_input` 으로 1순위와 동급(지역·업종·단계).
`pick()` 이 후보를 순서대로 훑어 첫 값을 고르므로 **추론이 사용자 입력을 덮는 경로는 구조적으로 없다** (테스트 B).

## 5. confirmed / inferred / unknown 처리

| 상태 | Context 에서 | 프롬프트에서 | 섹션 예외 |
|---|---|---|---|
| confirmed | 그대로 | "확정된 정보(사용자가 직접 적었거나 확인한 것)" 목록 | — |
| inferred | `source: ai_inference` | "AI 추정 참고정보(사용자가 확인하지 않음)" 목록, 값 뒤에 `(추정)` | `noInferred` 섹션 8개에는 **아예 전달하지 않음** |
| unknown | `unknowns[]` | "아직 정해지지 않은 것: … — 값을 만들지 말고 필요하면 '추가 정의 필요'로 둔다" | — |

프롬프트 규칙(§7 블록 원문) 으로 추정의 용법을 "조건형 언급만"으로 제한하고, 추정으로 숫자·시장규모·가격·성과·경쟁사·고객 행동을 만들지 못하게 한다. 기존 리얼리티 게이트(시스템 프롬프트)는 그대로 위에 있다.

## 7. Writer 프롬프트에 실제 추가된 블록 (A-class · overview/summary)

```
[이 사업의 구조화된 맥락]

확정된 정보(사용자가 직접 적었거나 확인한 것):
- 사업 유형: 교육·강의
- 핵심 고객: 반려견 보호자
- 고객의 문제: 기념일에 직접 만들어주고 싶지만 방법을 모름
- 핵심 상품·서비스: 반려견 케이크 원데이 클래스
- 수익 구조: 클래스 수강료
- 지역: 서울 마포구
- 진행 단계: 아이디어 단계
- 고객 유입 방식: 인스타그램, 유튜브 숏폼
- 판매 가격: 5만원
- 월 판매량(사용자 확인): 월 40건
- 수익 구조 태그: 수업·클래스

AI 추정 참고정보(사용자가 확인하지 않음):
- 전달 방식: 오프라인 대면 · 예약제 (추정)

이 사업 구조에서 생각할 것(관점 힌트이지 사실이 아님):
- 클래스 사업: 정원·수업 횟수·공간 확보·예약 방식·1인당 재료비·강사 역량이 매출과 비용을 결정한다. 값이 없으면 무엇을 정해야 하는지만 쓰고 숫자는 만들지 않는다.

계산된 재무 핵심값(시스템 계산 — 다시 계산하지 말고 인용만):
- 판매가 50,000원 / 변동비 18,000원 / 건당 공헌이익 32,000원 (이익률 64%)
- 손익분기: 월 16건 (매출 800,000원)
- 12개월 합계: 매출 24,000,000원, 영업손익 9,360,000원
- 월 흑자 전환: 1개월차

아직 정해지지 않은 것: 우리만의 강점 — 값을 만들지 말고 필요하면 '추가 정의 필요'로 둔다.

[맥락 사용 규칙]
- 확정된 정보는 사실로 사용할 수 있습니다.
- AI 추정 참고정보는 사업 구조를 이해하는 참고자료일 뿐입니다. 사용자가 확정한 사실처럼 쓰지 말고, 필요하면 '~를 고려할 경우' 같은 조건형으로만 언급하세요.
- 추정을 이용해 숫자·시장규모·가격·성과·경쟁사·고객 행동을 새로 만들지 마세요.
- 이 섹션 사용자 답변과 맥락이 어긋나면 사용자 답변을 우선합니다.
- 이 맥락은 이 섹션의 관점을 잡기 위한 참고입니다. 맥락을 그대로 요약해 반복하지 말고, 이 섹션의 목적에 필요한 정보만 쓰세요. 앞 섹션에서 이미 설명한 내용은 반복하지 마세요.
- 어느 사업에나 붙는 문장('혁신적인', '차별화된', '고객 만족 극대화', '시장 경쟁력 확보', '적극적인 홍보', '지속적인 성장')으로 문단을 채우지 마세요. 이 사업의 구조·사용자 답변·근거·계산값으로 구체적으로 쓰세요.
```
위치: `[해결되지 않은 답변 충돌]` 뒤, `[공식 원문 검색을 통해 확보한 시장 근거]` 앞. 시스템 프롬프트는 글자 하나 바뀌지 않는다(테스트로 고정 → 25섹션 캐시 유지).
블록 길이: 가장 큰 요약 섹션에서 **≈1,900자** (테스트 상한 2,200자). 분량 지침은 기존 그대로라 본문이 길어질 근거가 없다.

## 8. 충돌 · Evidence · 재무 결합

**충돌** — `buildPlanBusinessContext` 가 위저드 답과 VERIFY 확정값을 비교한다(고객·대표 상품·전달 방식). 공백 제거 후 다르고 포함 관계도 아니면:
```
- 핵심 고객이(가) 두 곳에서 다릅니다: 질문 답변 "프리미엄 베이커리 사장님" · AI 분석에서 확인한 값 "반려견 보호자" — 질문 답변을 기준으로 작성하되 확정 필요로 표기
```
이 항목이 기존 `conflicts` 배열에 합쳐져 `[해결되지 않은 답변 충돌]` 블록으로 간다. **Writer 에게는 위저드 값만** 간다(테스트 B). "반려견 보호자" ⊂ "30~40대 반려견 보호자 직장인" 같은 포함 관계는 충돌로 보지 않는다.

**Evidence** — `MarketEvidence` 는 기존 `evidenceForSection` → `formatEvidence` 경로 그대로. 맥락 블록에 근거를 다시 넣지 않는다 — 같은 수치가 두 블록에 있으면 "두 번 인용"과 "어느 쪽 규칙을 따를지" 문제가 생긴다. 근거 블록의 기존 규칙(목록 밖 수치 생성 금지·기관명+기준일·URL 불변·사용자 수치와 충돌 시 확정 금지)이 그대로 적용되며, 맥락 블록은 "추정으로 시장규모를 만들지 말라"로 양쪽을 잇는다. "양육가구의 10%가 구매" 같은 전환 추정은 두 규칙 모두에 걸린다.

**재무** — `finance.summary` 는 `financialsToReference(calculateFinancials(collectFinancialInputs(answers)))` — 기존 계산기 결과 그대로. "다시 계산하지 말고 인용만". 재무표·참고 블록이 이미 있는 섹션에선 빠진다. LLM 이 곱셈할 입력(정원·횟수)은 `operations.capacity` 로 "회당 6명 × 월 8회" 문자열만 주고, 판매량은 사용자가 확인한 `monthly_volume` 을 준다.

## 11. 테스트 사업 5종 · BEFORE/AFTER — 솔직한 상태

**실생성은 하지 못했다.** 로컬 `.env.local` 에 `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` 가 없고(운영 키는 Cloudflare secret), `/dev/*` 는 운영에서 404 라 우회 경로도 없다. 코드로 우회 경로를 만들지 말라는 원칙을 지켰다.

준비된 것:
- `scripts/plan-context-compare.ts` — 5개 사업(A 클래스 · B 쇼핑몰 · C 네일샵 · D SaaS · E 가구 제조) × 대표 섹션 2개, BEFORE(맥락 없음)/AFTER(맥락 주입) 생성 → **익명 A/B 순서 섞어** 심사 LLM 에 9개 기준(특화도·범용문장·고객/수익/운영 일관성·근거 없는 주장·숫자 환각·중복·계획서다움) + 환각 인용 요구 → `docs/compare/*.md` 와 `SUMMARY.md`. "길이로 우위를 주지 말라"를 심사 프롬프트에 명시.
- `docs/compare/` 10개 파일 — 지금은 각 사업·섹션의 **AFTER 프롬프트 블록만** 기록돼 있다.

실행 방법(키가 있는 곳에서):
```bash
ANTHROPIC_API_KEY=sk-ant-... npx tsx scripts/plan-context-compare.ts
```
→ 10섹션 × (BEFORE + AFTER + 심사) = LLM 30회, 약 5분.

프롬프트 수준에서 확인된 것(코드로 보장):
| 기준 | 보장 방식 |
|---|---|
| 숫자 환각 | 추정 블록에 숫자가 들어갈 수 없다(Analyzer 가 숫자를 unknown 으로만 냄 · `numericSlots` 는 confirmed 만) · 재무는 계산기 값만 · "다시 계산 금지" |
| 고객·수익·운영 일관성 | 25섹션이 같은 `PlanBusinessContext` 한 객체에서 읽는다. 섹션마다 다른 값을 볼 수 없다 |
| 범용문장 | 금지 어휘 6개를 블록에 명시 + 기존 시스템 프롬프트의 "복붙 가능한 범용 문장은 실패" |
| 중복 | "맥락을 그대로 요약해 반복하지 말라" + 기존 `priorSummary` |
| 길이 | 분량 지침 무변경 · 블록 ≤2,200자 |

## 13. 남아 있는 한계

1. **실생성 비교 미실행** — §11. 운영 키로 돌려야 "더 구체적인가"를 말할 수 있다. 지금 말할 수 있는 건 "환각이 구조적으로 막혀 있고, 불필요한 입력이 늘지 않았다"까지.
2. inferred 를 주는 섹션에서 Writer 가 "조건형" 규칙을 지키는지는 프롬프트 의존 — 위반 시 후처리 검사는 없다.
3. `contextConflict` 는 3개 필드(고객·상품·전달)만 비교한다. 가격·채널은 기존 `consistency.ts` 가 잡는 범위와 겹쳐 뺐다.
4. `venueCost` 를 2라운드 4개 안에 못 넣으면(important 등급) 고정비 합계 카드가 생기지 않는다 — 위저드에서 적으면 된다.
5. `operations.capacity` 가 `class` 팩에서만 채워진다(좌석형·SaaS 는 없음).
6. 섹션 간 "앞에서 이미 설명한 것"은 `priorSummary` 4,000자 절단에 의존 — 25섹션 뒤쪽은 앞 섹션 일부만 본다(기존 동작).
