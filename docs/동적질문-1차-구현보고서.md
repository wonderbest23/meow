## 3. Analyzer 실제 JSON Schema (Zod, `domain.ts`)

```ts
// 느슨하게 받고(필드 누락·오타 허용) normalize 에서 엄격하게 굳힌다
rawAnalysisSchema = z.object({
  primary:             strField,   // {value?: string|null, status?: string, confidence?: 0~1}
  modelTags:           arrField,   // {value?: string[]|null (≤12), status?, confidence?}
  operationTags:       arrField,
  customer:            strField,
  problem:             strField,
  solution:            strField,
  revenueModel:        strField,
  deliveryModel:       strField,
  acquisitionChannels: arrField,
  keyCosts:            arrField,
  stage:               strField,
  region:              strField,
  gapHints:            z.array({ slot: string(≤60), why: string(≤120) }).max(10),
  summaryForUser:      z.string().max(400),
}).partial-ish
```

**normalize 규칙 (테스트로 고정)**

| 입력 | 결과 |
|---|---|
| `status: "confirmed"` | confirmed |
| 그 외 어떤 문자열(`"inferred"`, `"definitely"`, 누락) | **inferred** — 승격은 절대 없다 |
| `value` 비어 있음 | `{value:null, status:"unknown"}` |
| `primary` 가 9종 밖 | `"기타"` |
| `modelTags`/`operationTags` 가 사전 밖 | **폐기** (`["class","newAmazingTag"]` → `["class"]`) |
| `summaryForUser` 없음 | 전체 실패(null) → 폴백 |
| JSON 파싱 실패 | null → 폴백 |

서버에서 사용자가 이미 고른 업종·지역·단계가 있으면 그 값을 `confirmed` 로 덮는다 — 사람이 고른 것이 추론보다 우선.

## 5. 질문팩 3개

**공통 슬롯 (모든 팩)** — 분석이 confirmed 로 못 채우면 묻는다

| id | 등급 | mapsTo |
|---|---|---|
| `customer` | blocking | `market/segments.first_target` |
| `problem` | blocking | `overview/problem.problems[]` |
| `solution` | blocking | `overview/problem.solutions[]` |
| `differentiator` | important | `market/competitors.differentiator` |
| `ownerExperience` | important | `summary/executive.why_us` |

**class (교육·클래스)** — `modelTags ∋ class` 또는 업종=교육·강의

| id | 질문(기본) | 등급 | mapsTo / alsoSet |
|---|---|---|---|
| `classPrice` | 1인 수강료는 얼마 정도로 생각하고 계세요? | blocking | `financials/revenue.unit_price` · `market/products.has_price=yes` |
| `seatsPerClass` | 한 번 수업할 때 최대 몇 명까지 받을 생각인가요? | blocking | (파생 계산용) |
| `classesPerMonth` | 한 달에 수업을 몇 번 정도 열 계획인가요? | blocking | (파생 계산용) |
| `venueType` | 수업 공간은 어떻게 마련할 계획인가요? | blocking | — (`__analysis` 에만) |
| `materialCost` | 수강생 한 명당 재료비가 대략 얼마나 들 것 같나요? | blocking | `financials/expenses.variable_per_unit` · `variable_items=[재료·원가]` |
| `occupancyRate` | 평균적으로 정원의 몇 % 정도 올 것 같나요? | important | (파생 계산용) |
| `venueCost` | 공간에 드는 돈은 한 달에 얼마쯤일까요? | important | `financials/expenses.fixed_total` · `fixed_items=[임대료]` |

파생: **월 수강생 = 정원 × 월 횟수 × 참석률(없으면 100%)** → 화면에서 산식과 함께 확인 → 확인 시에만 `financials/revenue.monthly_volume`

**commerce (온라인 판매)** — `modelTags ∋ commerce` 또는 업종=온라인 쇼핑몰

| id | 등급 | mapsTo |
|---|---|---|
| `aov` 1회 평균 구매 금액 | blocking | `unit_price` · `has_price=yes` |
| `monthlyVisitors` 월 방문자 | blocking | (파생) |
| `conversionRate` 구매 전환율 (1%/2%/3%/5%) | blocking | (파생) |
| `cogs` 상품 원가+포장·배송 | blocking | `variable_per_unit` · `variable_items` |
| `adBudget` 월 광고비 | important | `strategy/promotion.promo_budget` · `has_promo_budget=yes` |
| `fixedOps` 월 고정비 | important | `fixed_total` |

파생: **월 판매 = 방문자 × 전환율**

**unit_sale (기본 폴백)** — 나머지 전부

| id | 등급 | mapsTo |
|---|---|---|
| `unitPrice` | blocking | `unit_price` · `has_price=yes` |
| `monthlyVolume` | blocking | `monthly_volume` |
| `unitCost` | blocking | `variable_per_unit` |
| `fixedTotal` | blocking | `fixed_total` |

## 6. 저장 방식

```
plan.answers["__analysis"] = {
  analysis:   BusinessAnalysis,          // 모든 필드 {value,status,confidence?}
  slots:      { [slotId]: { value: string|null, status: "confirmed"|"unknown" } },
  rounds:     0 | 1 | 2,
  finished:   boolean,
  analyzedAt: ISO
}
```

- `normalizeState()` 는 `answers` 를 키 검사 없이 통과시킨다 → **마이그레이션 불필요** (확인: `plan-server-store.ts:81`)
- 진행률은 blueprint 섹션만 센다 → `__analysis` 는 **진행률 0 영향** (테스트 J · 실측 §8)
- `createPlan({inheritAnswers})` 가 답변을 통째로 복사하므로 이어받기에 자연히 포함된다
- 저장 경로는 기존 `plan-store.saveAnswers()` 하나. API 는 저장하지 않는다.

**VERIFY 확정값 → 기존 칸 (`applyAnalysisToAnswers`, confirmed 만)**

| 분석 필드 | → 기존 답변 칸 |
|---|---|
| `customer` | `market/segments.first_target` |
| `problem` | `overview/problem.problems[]` |
| `solution` | `overview/problem.solutions[]` · `market/products.main_offer` |
| `deliveryModel` | `strategy/distribution.delivery` |
| `modelTags` | `financials/revenue.revenue_streams[]` (class→시간·건당 요금, subscription→정기 구독·회원 …) |
| `acquisitionChannels` | `strategy/promotion.promo_channels[]` (기존 7개 선택지로 매핑, 안 맞으면 버림) |

**inferred 는 어디에도 쓰지 않는다** (테스트 C · 실측: 고객을 미확인으로 두자 `market/segments` 가 비어 있음).
이미 답이 있는 칸은 덮지 않는다 — 위저드에서 직접 적은 답이 우선.

## 7. 실제 UX 흐름

```
/plan/start  ① 사업 정보  ② 플랜 유형 선택 (기존 그대로)
      │  pick() → createPlan()
      ▼
/plan/analyze
  [AI 분석]      "사업 설명을 읽고 구조를 분석하는 중…"   ── LLM 1회
      ▼
  [이해 확인]    "말씀해주신 내용을 이렇게 이해했어요."
                 요약 한 문장 + 항목 3~6개 (값 있는 것만):
                 사업 유형 · 고객 · 제공하는 것 · 운영 형태 · 수익 구조 · 고객 유입
                 각 행: [맞아요] [바꿀래요] — confirmed 면 "✓ 확인됨"(초록), inferred 면 "AI가 추측한 내용이에요"
                 [다음 — 몇 가지만 더 여쭤볼게요 →]   [건너뛰고 직접 작성하기]
      ▼
  [질문 1/2]     최대 4개 · blocking 우선 · 카드마다 "왜 묻는지" 한 줄
                 number: 직접 입력(+AI 범위 보기) / single: 칩 / text: 서술
                 모든 카드에 [아직 모르겠어요]
                 "사업 구조 완성도 ▓▓░░ 38%"
                 [n/4 답함 · 다음 →]   [지금 정보로 작성하기]
      ▼ 규칙 재계산(LLM 없음) → 남은 blocking 있으면
  [질문 2/2]     (최대 4개)                                  ── LLM 1회
      ▼
  [숫자 확인]    "월 약 48명 — 정원 6명 × 월 8회 = 약 48명"   (파생값은 여기서 확인해야 저장)
                 [이 숫자로 할게요 →]   [건너뛰기 — 나중에 직접 입력]
      ▼
  [준비 완료]    핵심 정보 확보 88% · 질문 팩 · 나중에 정할 것 n개
                 [플랜 개요로 — 시장자료·재무 확인·생성 →]
      ▼
/plan/overview   공식 시장자료(기존) → 재무 확인(기존) → 생성(기존)
                 매핑된 섹션은 "작성 중" 표시. 분석 안 거친 빈 플랜엔 "AI와 정리하기" 권유 카드.
```

실패 화면: "AI 분석을 완료하지 못했어요. … 직접 정보를 입력해서 계속할 수 있습니다." → [직접 입력해서 계속하기 →] [다시 분석하기]

| 숫자 확인 | "월 약 48명 / 정원 6명 × 월 8회 = 약 48명" 표시 → 확인 후에만 `monthly_volume: "월 48건"` |

| 저장 검증 | `unit_price "5만원"` · `variable_per_unit "1만5천원"` · `problems[]` · `solutions[]` · `main_offer` · `revenue_streams ["시간·건당 요금"]` · `promo_channels ["인스타그램","유튜브·숏폼"]` · `differentiator` · `has_price "yes"`. **inferred 로 남긴 고객은 `market/segments` 에 없음** |
| /plan/overview | 진행률 0/25(= `__analysis` 미집계) · 매핑된 7개 섹션 "작성 중" · 분석 없는 빈 플랜엔 권유 카드 표시 |

실측 중 잡은 버그 1건 → 수정: 85% 비율만 보면 **재료비(blocking) 하나가 남았는데 종료**됐다. 종료 판정을 "남은 blocking 0개 + 5대 축 confirmed" 로 바꿨다(비율은 표시용).

### 타입
`npx tsc --noEmit` 통과.

## 12. 2차에서 해야 할 것

1. **운영 실측** — 실제 Claude 응답으로 confirmed/inferred 구분이 프롬프트 의도대로 나오는지 10건 샘플링. 과도하게 confirmed 로 찍으면 프롬프트 보강.
2. **`section-generator` 에 분석 요약 주입** — `SectionGenInput.context?` 한 필드(evidence 패턴). inferred 는 "추정" 표기로만.
3. **질문팩 확장** — SaaS(`subscription`) · 좌석형(`seat`) 부터. 팩당 슬롯 6~7 + 파생 1.
4. **재무 확인 화면 연결** — `venueType`·`occupancyRate` 같은 `__analysis` 전용 슬롯을 `FinancialReview` 가정 목록에 표시.
5. **위저드 쪽 표시** — 동적 답으로 채워진 칸에 "AI 상담에서 답한 값" 배지(출처 표시).
6. **중복 질문 통합** — 설계서 §C 의 27개. 동적 경로가 안정되면 위저드에서도 한 번만 묻도록.
7. **기능 플래그** — 현재는 `/plan/start` 가 새 사업이면 항상 `/plan/analyze` 로 간다. 롤백이 필요하면 `pick()` 의 한 줄을 되돌리면 된다(플래그 환경변수는 두지 않았다 — 코드로 우회 경로를 늘리지 않기 위해).

## 부록. 핵심 불변식 (코드 주석에도 같은 말이 있다)

```
inferred  → [맞아요] 전까지 기존 답변 칸에 쓰지 않는다 (applyAnalysisToAnswers 는 confirmed 만)
unknown   → 값 없음 그대로. AI 가 숫자를 채우지 않는다. 리얼리티 게이트가 "추가 정의 필요"로 처리
slot id   → 팩 화이트리스트 밖이면 어디서 와도 저장하지 않는다 (applySlotAnswer · question-generator)
tag       → 사전 밖이면 폐기 (normalizeAnalysis)
파생 숫자  → 산식을 보여주고 사용자가 확인한 뒤에만 monthly_volume 에 저장
실패      → 어느 단계든 /plan/overview 로 — 기존 위저드가 그대로 있다
```
