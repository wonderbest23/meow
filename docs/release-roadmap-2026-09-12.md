# 출시 보완 실행 계획

기준일: 2026-09-12. 디자인 변경과 기능 검증은 별개로 판단한다.
이 문서의 완료는 코드, 모의 검증, 실제 서비스 검증, 운영 배포를 각각 구분한다.

## 현재 기준선

- 1차 보완: PPT 생성 제한, 오류 구분, 중복 요청 방지, 작업 복구와 모의 회귀 검증 완료.
- 실제 OpenAI 생성 및 전체 슬라이드 렌더링 검증: 미완료.
- 실제 로그인부터 PG 승인과 재접속까지 연결 검증: 미완료.
- 홈페이지 디자인은 로컬 반영 상태이며 기능 안정성을 보장하는 근거가 아니다.
- 이번에 보완한 결함: 일반 프로젝트 귀속과 달리 `plan_states`의 서버 대화/작업 기록은 로그인 계정으로 이전되지 않았다.
- 이번에 보완한 결함: 로컬 캐시는 인증 여부만 기억해 로그인한 A 계정에서 B 계정으로 전환한 경우를 구별하지 못했다.
- 후속 로컬 격리 검증: 실제 Supabase Auth/PostgreSQL 시나리오 17/17 통과. 토큰 길이 오판과 기존 프로젝트 이전 실패 후 복구 누락을 수정했다. [상세 결과와 재현 절차](./local-account-integration-2026-09-12.md).
- `PLAN_ACCOUNT_LINKING_ENABLED`는 원본/운영에서 기본 비활성이다. 마이그레이션과 활성화는 격리된 로컬 DB/앱에만 수행했으며 운영 배포하지 않았다.

## 실행 순서와 완료 조건

### 1. 데이터 소유권 연결 (이번 차수)

- [x] 서버의 비회원 사업, 코치 대화, 생성 문서, 실패 작업 초안을 로그인 계정으로 원자적으로 병합하는 코드를 추가했다.
- [x] 같은 비회원 데이터는 한 계정에만 귀속하며 재요청은 중복 복사하지 않는다.
- [x] 이전 중 데이터가 바뀌면 최신 상태를 다시 읽으며, 진행 중인 AI 작업은 끝난 후 로그인하도록 안내한다.
- [x] 계정별 캐시 표식을 도입하고 이전 계정의 지연 저장/재시도를 서버에서도 거절한다.
- [x] 신규 플랜 이전 실패를 비밀번호 오류와 구분했다. 가입 완료/비밀번호 변경 후 이전 실패도 이미 완료된 작업을 안내한다.
- [x] 모의 회귀 20개 묶음 및 독립된 SQL 엔진에서 이전, 충돌 후 재시도, 원본 복구, RPC 접근 제한을 검증했다.
- [x] 로컬 Supabase에서 이메일 로그인/가입/인증 콜백/비밀번호 복구, 계정 전환, 실제 DB 잠금 경합, 이전 실패 후 재로그인 복구를 17개 통합 시나리오로 검증했다.
- [ ] 브라우저 다중 탭 및 외부 스테이징의 Google/이메일 확인/Cloudflare 환경을 검증한다.
- [ ] 운영 배포 및 배포 후 비회원/회원 흐름을 확인한다.

배포 조건: 아래 스테이징 점검을 먼저 통과한다. 운영 DB에는 승인 없이 적용하지 않는다.

#### 바로 다음 실행: 스테이징 데이터 연결 검증

1. 운영과 분리된 Supabase 프로젝트, 이메일 계정 A/B와 Google 테스트 계정, 테스트 배포 URL을 정한다.
2. `supabase/migrations/0027_plan_account_linking.sql`과 `0028_account_link_retry.sql`을 스테이징에 적용한다.
3. 웹/API/Workflow의 모든 저장 실행기를 새 버전으로 맞춘 뒤 `PLAN_ACCOUNT_LINKING_ENABLED=true`를 켠다. 구버전 직접 저장 경로와 새 SQL 잠금 경로가 섞인 상태는 허용하지 않는다. 구버전 브라우저의 미전송 내용 보존과 새로고침 이후 복구도 활성화 전에 확인한다.
4. 비회원으로 대화, 직접 수정한 문서, 실패한 PPT 초안을 준비한다. 로그인 후 사업 ID, 대화 개수, 코치 버전, 본문, 잠금, 초안을 이전 전후 대조한다.
5. 같은 비회원 세션의 로그인 재시도, 계정 A/B 전환, 오래 열린 탭의 저장/화면 종료, 세션 만료, 이전 직후 응답 유실을 확인한다.
6. 실제 DB 병렬 트랜잭션에서 저장과 이전을 겹쳐 실행한다. 로컬 PostgreSQL의 다중 연결 잠금 경합과 동시 계정 이전은 통과했으며 배포 런타임에서도 재확인한다.
7. 기존 `projects`, `payment_orders`, `opportunity_preferences`도 대조한다. 새 원자적 이전의 범위는 `plan_states`와 `plan_owner_claims`이며, 기존 세 테이블은 별도 처리다. 로컬에서는 후속 실패/쿠키 교체/다른 계정 격리/재로그인 복구를 확인했다. `legacy_completed_at`으로 계정별 미완료 작업을 재개하는 버전이 배포되어야 한다.

합격 증거: 각 시나리오의 입력 상태, 결과 상태, HTTP 상태/오류 코드, 사업/작업/주문 식별자와 재현 절차를 기록한다. 비밀번호, 인증 토큰, 원문 대화는 점검 로그에 남기지 않는다.

### 2. PPT 실제 생성

선행 조건: 테스트 계정과 저장 사업, OpenAI 프로젝트 잔액/지출 한도, 테스트 비용 상한 확정.

1. 8~10장 생성과 검토를 한 번 실행하고 단계 시간, 모델, 토큰, 결과 작업 ID를 기록한다.
2. 실제 PPTX를 내려받아 모든 슬라이드를 렌더링하고 한글, 잘림, 겹침, 출처와 숫자를 확인한다.
3. 재접속/다른 탭에서 같은 파일을 다시 내려받고 추가 생성 호출이 없는지 확인한다.
4. 타임아웃 및 파일 제작 실패 후 저장된 단계에서만 재개되는지 확인한다.

통과 조건: 생성, 품질 검토, 재다운로드, 실패 복구 모두 통과. 그전에는 PPT 준비 중 표시 유지.
실패 시: 원인을 잔액/요청 제한/시간/문서 품질로 나눠 해당 단계만 보완한다. 성공할 때까지 무제한 반복 생성하지 않는다.

### 3. 로그인과 결제 종단 간 검증

PG 테스트 모드에서만 진행한다. 실제 결제 승인은 사용자 확인이 필요하다.

- 비회원 대화 -> 로그인 -> 같은 사업 ID와 코치 대화 복원 -> 결제 -> 해당 사업 권한 -> 재로그인.
- 로그인 취소, 잘못된 비밀번호, 세션 만료, 계정 A/B 교체, 두 탭의 오래된 저장.
- 승인/취소/실패, 중복 클릭, 중복/순서 역전 콜백, 승인 후 DB 장애, 환불과 권한 회수.
- 문서 상품과 홈페이지 상품의 권한이 서로 열리지 않는지 확인.

통과 조건: 다른 계정 데이터 노출 0건, 사업 유실 0건, 중복 승인 0건, 주문 상태와 권한 일치. 실패 사례에는 재현 절차와 복구 결과를 남긴다.

### 4. 운영 장애와 비용 관리

관리자 읽기 전용 작업 목록부터 만든다. 실패 단계/오류 코드/저장된 결과/재개 가능 위치/소요 시간/토큰 사용량을 제공한다.
이후 운영 알림 채널, 일별 사용 예산, 중복 알림 억제와 수동 재시도 권한을 추가한다.
원문 대화나 API 키는 로그에 남기지 않으며 토큰 사용량과 실제 청구 금액은 구별한다.

통과 조건: 의도한 실패 1건이 작업 목록과 알림에 한 번씩 나타나고 재처리 이력과 복구 상태가 연결된다.
외부 테스트 환경을 기다리는 동안에는 이 단계의 읽기 전용 목록과 모의 알림 검증을 먼저 진행할 수 있다. 임의로 알림 수신자나 비용 예산을 정하지 않는다.

### 5. 맞춤 홈페이지 제작 연결

먼저 제공 범위, 담당자, 견적/납기/수정/환불 정책을 확정한다.
요청 접수 -> 운영자 견적 -> 고객 승인 -> 담당자 배정 -> 진행 상태 -> 결과물 확인 순서로 구현한다.
마케팅/세무/사무실 지원은 실제 제공 체계가 생기기 전까지 확장하지 않는다.

통과 조건: 테스트 요청 1건이 전 단계를 통과하고 고객과 운영자가 같은 상태 및 결과물을 확인한다.

## 공통 릴리스 절차

1. 타입/회귀/빌드 검증 및 변경 범위 확인.
2. 스테이징 DB 마이그레이션과 기능 플래그 적용.
3. 실제 계정과 테스트 PG에서 사용자 시나리오 확인.
4. 사용자 승인 후 운영 배포, 버전과 점검 결과 기록.
5. PPT 등 독립 기능은 오류 증가 시 비활성화한다. 계정 이전이 한 번이라도 실행된 환경은 이전 보호를 유지해야 하므로 계정 연결 플래그만 끄거나 구버전으로 되돌리지 않는다. 신규 로그인/쓰기를 일시 중단한 상태에서 소유권 보호를 유지하는 수정 버전으로 복구한다. 이전된 자료를 비회원에게 되돌리는 파괴적 롤백은 하지 않는다.

외부 승인/환경이 없어도 진행 가능한 모의 검증과 운영 화면 구현은 계속할 수 있지만, 이를 실제 결제/API 검증 완료로 기록하지 않는다.

| 외부 스테이징/Google/PG/API 과금 | 미실행 | 스테이징 및 테스트 허용 범위 확정 후 진행 |
| 운영 마이그레이션/배포 | 미실행 | 릴리스 조건 통과 및 승인 후 진행 |

SQL 테스트 재현: 앱 의존성과 분리해 `@electric-sql/pglite@0.5.8`을 임시 디렉터리에 설치하고 `PGLITE_TEST_MODULE`에 `dist/index.js` 절대 경로를 지정한 뒤 `node --import tsx scripts/plan-account-linking.sql.test.mts`를 실행한다. 실제 DB 연결 없이 메모리 내 테스트 데이터만 사용한다.

빌드의 기존 경고: `middleware` 파일 규약 폐기 예정, 로컬 개발의 Workflow 바인딩 제한. 배포 환경에서 Workflow 실행 확인이 별도로 필요하다. 로컬 서버는 `http://localhost:8083`에서 다시 실행 중이다.
