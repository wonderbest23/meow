# 실제 기능 구현과 출시 준비 점검

출시 검증 최신 상태: 로컬 Auth/PostgreSQL 21개, 회귀 34개, PC/모바일 관리자 화면, 격리 Next 프로덕션 빌드를 확인했다. 실제 AI 분석/9장 PPT 생성과 로컬 인증/권한/재다운로드 15개도 통과했다. 홈페이지 생성/공개/복원/문의 16개와 인증된 홈페이지 브라우저 흐름은 [홈페이지 전체 연결 검증](./homepage-lifecycle-verification-2026-09-13.md)에 추가했다. [출시 검증 현황](./launch-validation-2026-09-13.md)과 [PPT 다운로드 검증](./local-deck-download-2026-09-13.md)에 범위를 구분해 정리했다. 결제 상태는 로컬 모의이며 Google/실제 PG/Cloudflare 검증과 운영 배포는 아직 완료하지 않았다.

후속 상태: 아래 내용은 최초 점검 당시의 기록이다. 같은 날 진행한 홈페이지 데이터 변환과 서버 저장/충돌 보완 결과는 [홈페이지 저장 검증 기록](./homepage-save-verification-2026-09-13.md)에, 템플릿 사업 문구 반영과 편집 검증은 [사업 내용 반영 검증](./homepage-business-content-2026-09-13.md)에 구분해 정리했다. 최신 대화에서 기존 홈페이지로의 갱신과 실제 운영 리포트는 여전히 후속 작업이다.

추가 후속 상태: 세 사용자 유형의 로컬 연결, 운영 단계 유지, 기록을 남기는 운영 개선 전환, 문서 재생성 저장 경합은 [사업 재방문/운영 개선 검증](./business-journey-verification-2026-09-13.md)에 정리했다. 기간별 리포트와 실제 유료 AI 결과물 검증은 포함하지 않는다.

최신 후속 상태: 기간별 실적 저장, 이전 기간 비교, 사용자 작성 개선 계획의 버전별 리포트 보관/Markdown 다운로드를 [운영 기록 검증](./operating-records-verification-2026-09-13.md)에 정리했다. 이는 AI 자동 분석 리포트 완성이나 실제 AI/PPT/결제 통과를 뜻하지 않는다. 아래 표와 본문은 최초 점검 시점의 상태를 유지한다.

AI 개선안 후속 상태: 전송 미리보기/명시적 동의, 기간 기반 가설 제안, 사용자 행동 선택/수정, 분석 입력과 리포트별 보관을 연결하고 [AI 개선안 격리 검증](./operating-analysis-verification-2026-09-13.md)에 정리했다. 29개 회귀 묶음과 로컬 HTTP/브라우저 모의 검증을 통과했으나 실제 분석은 기본 비활성이다. 실제 AI 품질, 스테이징 Google/DB, PPT/결제 검증은 여전히 남아 있다.

기준일: 2026-09-13. 현재 로컬 작업본의 코드, 기존 검증 기록, 이번 모의 테스트를 대조했다.
운영 서버의 배포 버전이나 설정이 같다고 가정하지 않는다. 이번에는 앱 기능을 수정하거나 운영 DB, 실제 AI, 로그인, 결제, 홈페이지 공개를 실행하지 않았다.

## 결론

대화로 사업안을 만들고 수정하는 기능, 문서 관리, 홈페이지 에디터의 기반은 구현되어 있다.
하지만 전체 고객 여정과 반복 운영 개선 리포트까지 완성된 유료 플랫폼으로 판단할 근거는 부족하다.
현재 판단은 제한된 베타 검증 단계다. 구현률 백분율보다 아래의 구현, 연결, 검증 상태를 기준으로 출시 범위를 정한다.

## 이번에 확인한 우선 보완점

### 1. 대화 사업안에서 홈페이지로 넘어가는 데이터 연결 누락

- 대화는 `answers.__business_coach.state.fields`에 `offer`, `customer`를 저장한다.
- `app/api/plan/chat/route.ts`의 문서 준비는 섹션 답변에 `planning_source`만 넣는다.
- `lib/landing/from-plan.ts:165`의 준비 검사는 기존 설문의 `market/products.main_offer`, `market/segments.first_target`만 읽는다.
- 홈페이지 생성 라우트도 이 검사/변환을 그대로 사용한다.
- 순수 함수 재현 결과: 대화 `ready=true`, 상품 `메뉴 사진 5장`, 고객 `동네 음식점`인데 홈페이지는 `ready=false`, 두 항목 누락으로 판정했다. 검사를 건너뛴 변환에서도 상품이 `상담 안내` 기본값으로 떨어졌다.
- 기존 설문형 샘플이 정상으로 보이는 것만으로 현재 대화 경로를 통과했다고 판단할 수 없다.

처리: 선택 사업의 최신 대화/설문 정보를 읽는 공통 변환을 마련하고, 준비 검사와 홈페이지 콘텐츠에 동일하게 적용한다. 사업 A/B, 신규/운영 중, 샘플, 누락 값, 기존 홈페이지 수동 수정 보존을 함께 검사한다.

### 2. 에디터의 저장 경험과 장애 복구

- `components/brainwave-editor.tsx:444`의 저장은 상위 `onSave`를 호출한다.
- `app/plan/homepage/page.tsx:335`는 초안 React 상태만 바꾸고 편집기를 닫는다. 서버 저장은 바깥 화면의 별도 저장/공개 동작이다.
- 따라서 편집기에서 저장을 눌렀다는 이유만으로 새로고침 후 보존된다고 보장할 수 없다.
- 같은 파일의 저장/공개 함수에는 네트워크 예외를 복구하는 `try/catch/finally`가 없다. HTTP 오류는 처리하지만 요청 자체가 실패하면 진행 상태가 남을 위험이 있다. 코드 검토로 확인했으며 브라우저 장애 주입은 미실행이다.
- 홈페이지 저장 API/저장소는 현재 초안 전체를 upsert하며 요청 기준 버전 비교가 없다. 동시 탭 편집 덮어쓰기 방어를 별도로 점검/보완해야 한다.

처리: 실제 서버 저장까지 하나의 동작으로 연결하고, 미저장/저장 중/저장 완료/실패를 구별한다. 이탈 보호, 재시도, 계정 전환, 오래된 탭 충돌, 이미지 업로드 중 저장을 검증한다.

### 3. 창업 이후 운영 단계로 이어지는 문서 정책

- 운영 중 진입은 별도 프롬프트와 `사업 운영·개선 계획서` 목차가 있다.
- `lib/plan-builder/coach-job.ts:47`은 문서가 없는 경우에만 사업 단계에 맞춰 문서 유형을 변경한다.
- 이미 일반 계획서를 만든 사업이 이후 운영 중으로 전환되면 기존 문서 유형은 유지된다. 본문은 최신 운영 맥락으로 바뀔 수 있지만, 운영 개선 리포트로 전환/추가하는 별도 사용자 흐름은 확인되지 않았다.

처리: 과거 계획서는 보존하고, 같은 사업 아래 새 기간의 운영 개선 리포트를 추가하는 방식으로 명확히 한다. 자동 덮어쓰기로 해결하지 않는다.

### 4. 지속 개선은 메모가 아니라 기간별 이력으로 연결해야 함

- `LaunchWorkspace`는 `records[current.id]`에 단계별 최신 메모와 자료를 저장한다.
- `review` 단계에서 실제 문의, 판매, 매출, 지출, 고객 의견을 적고 기존 사업의 AI 대화로 이어갈 수 있다.
- 이것만으로 주간/월간 지표 누적, 이전 기간 비교, 개선 효과 평가, 리포트별 다운로드 이력이 완성된 것은 아니다.
- 별도 `execution-loop`/`operations` 엔진과 패널은 존재하지만 현행 `/plan/workspace`에는 렌더링되지 않는다. `app/page.tsx`에는 해당 패널의 import만 있으며 JSX 사용은 없다.
- 예전 프로젝트 결과물의 수정 이력 코드도 현재 대화형 사업 관리의 완료 근거로 대신 사용할 수 없다.

권장 흐름: 같은 사업 선택 -> 기간별 실제 결과 입력 -> 이전 기간과 비교 -> 원인 가설/개선안 제시 -> 사용자가 실행안 선택 -> 다음 기간 결과 기록 -> 새 리포트 저장/다운로드. 사용자 입력 실적, 예상값, AI 제안을 계속 구분한다.

## 에디터 애니메이션 방향

기존 에디터를 유지하면서 다음 상호작용을 추가할 수 있다.

1. 선택한 글/사진만 파란 테두리와 작은 도구막대로 표시한다.
2. PC는 옆 편집 패널, 모바일은 키보드와 겹치지 않는 하단 패널을 사용한다.
3. 변경 내용은 미리보기에 즉시 반영하며 포커스와 커서를 유지한다.
4. 적용된 위치만 짧게 강조하고, AI 수정은 변경 전후 확인과 한 번의 되돌리기를 제공한다.
5. 저장 성공 표시는 서버 응답 이후에만 표시한다. 애니메이션이 저장을 대신하거나 입력을 지연시키지 않게 한다.
6. 긴 한글, 긴 버튼 이름, 세로 사진, 업로드 실패, 모바일 키보드, 동작 줄이기를 함께 검증한다.

6. **테스트 결제와 홈페이지 공개**: 상품별 권한, 승인/취소/중복/환불, 편집/공개/재공개/복원 및 문의 수신을 스테이징에서 확인한다.
7. **운영 준비 후 제한 출시**: 작업/오류/비용 확인, 알림, 고객 문의, 복구 절차를 갖추고 검증된 범위만 판매한다.

스테이징 마련은 1-3과 동시에 준비할 수 있다. 정기 개선 리포트를 출시 상품에 포함하지 않을 경우 3은 후속 단계로 분리하되, 현재 제공되는 것처럼 표시하지 않는다.
