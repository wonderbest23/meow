# 사업계획서 기능 구현 현황 보고서

> **조사 기준**: 코드베이스 직접 확인 (2026-08-22)
> **저장소**: `wonderbest23/meow` — 오늘창업 (oneulstart.com), Next.js 16 + Cloudflare Workers(OpenNext) + Supabase
> **원칙**: 추측 없음. 코드·DB·프롬프트·컴포넌트를 직접 읽고 확인한 내용만 기재. 없는 것은 `미구현`으로 명시.
> **주의**: 이 문서는 향후 재설계를 위한 현황 스냅샷입니다. 조사 중 코드는 일절 수정하지 않았습니다.

## 1. 전체 사용자 흐름

```
① /plan (목록)  → ② /plan/start (유형+사업정보) → ③ /plan/overview (구조)
→ ④ /plan/{chapterId}/{sectionId} (질문 위저드) → ⑤ 생성 큐 → ⑥ /plan/document (완성 문서)
→ ⑦ 편집 / ⑧ /api/plan/document (PDF·DOCX 다운로드)
```

| 단계 | URL | 컴포넌트 | API | 서버 함수 | 저장 |
|---|---|---|---|---|---|
| ① 목록 | `/plan` | `app/plan/PlanList.tsx` | `GET /api/plan/state` | `loadPlanState()` | `plan_states` |
| ② 시작 | `/plan/start` | `app/plan/start/page.tsx` | — | `createPlan()` (클라이언트) | localStorage → PUT |

| ⑤ 생성 | (백그라운드) | `lib/plan-builder/generation-queue.ts` | `POST /api/plan/generate` (NDJSON 스트리밍) 또는 `POST /api/plan/queue` (Cloudflare Workflow) | `generateSection()` / `generateAndSaveSection()` | `plan.sections[key]` |

### 중요 특징

- **로그인 → 사업 아이템 입력 순서가 아님.** 로그인 없이 시작 가능하고, 무료 2개 섹션까지 생성 후 `402`로 결제 요구
  (`lib/plan-builder/access.ts:9` `FREE_SECTION_COUNT = 2`, `FREE_PLAN_LIMIT = 3`).
- **"AI 한 번 호출 → 계획서 완성"이 아님.** 섹션당 1회씩, 총 **25회 LLM 호출**(유형에 따라 10~25회).
  순차 실행이며 앞 섹션 요약(`priorSummary`)이 뒤 섹션에 전달됨.
- 가격: 모든 유형 **149,000원** (`lib/payments/plan-orders.ts:47-56`).

## 3. 추가 질문 / 역질문 시스템

### 현재 역질문 시스템 없음 (🔴 미구현)

AI가 사용자에게 되묻는 기능은 존재하지 않습니다. 질문은 138개 전부 코드에 하드코딩되어 있습니다.

**대신 존재하는 두 가지 (혼동 주의)**

#### ① `showWhen` 조건부 분기 — 규칙 기반, AI 아님

```ts
{ id: "started_when", q: "언제 시작하셨나요?", showWhen: { qid: "established", equals: "yes" } }
```

`lib/plan-builder/questions.ts:874` `isVisible()`.
모듈 로드 시 분기 무결성을 검증하는 방어 코드까지 있음 — 부모 질문이 유형 필터로 빠지면 `throw`.

#### ② `aiSuggest` — AI가 "답안 후보"를 제안

`app/api/plan/suggest/route.ts`

- 질문이 아니라 **답변 초안 2~6개**를 JSON 배열로 제안
- `maxOutputTokens: 700`, `effort: "low"`, provider `anthropic` 우선
- 서버가 저장된 플랜에서 사업 맥락을 직접 읽어 프롬프트에 주입 (화면이 보낸 맥락만 믿지 않음)
- 저장: 사용자가 고르면 일반 답변과 동일하게 `plan.answers`에 저장

## 4. AI 프롬프트 전체

### 4-1. 섹션 생성 시스템 프롬프트 (가장 중요)

- **파일**: `lib/plan-builder/section-generator.ts:9-20`
- **함수**: `sectionSystemPrompt()`
- **시점**: 섹션 생성 시마다 (플랜당 최대 25회)
- **모델**: Claude Sonnet 5 (기본), OpenAI 폴백

```text
당신은 한국에서 실제로 실행할 사업계획서의 한 섹션을 작성하는 선임 사업전략가입니다.
이 작업은 소설·광고 창작이 아닙니다. 오직 사용자가 제공한 답변만 확정 사실로 사용할 수 있습니다.
고객 인터뷰·설문·매출·시장규모·성장률·경쟁사 실명·수상·특허·제휴·후기를 절대 만들어내지 마세요.
근거가 없는 수치나 주장은 반드시 '추가 정의 필요' 또는 '검증 필요'로 표기하고, 미래형·조건형 문장을 사용하세요.
다만 그 표기를 문장마다 반복하지 마세요. 본문에서는 미확정임이 드러나게 서술만 하고, 섹션 끝에
'추가 정의 필요 항목' 목록 하나로 모으세요. 같은 표기가 한 섹션에 세 번을 넘으면 실패로 간주합니다.
그 목록의 각 항목에는 '어디서 어떻게 확인하는지'를 한 줄로 붙이세요. 모른다고만 하는 문서는 읽는 사람이
다음 행동을 할 수 없습니다. 예: 상권·유동인구는 소상공인 상권정보시스템(sg.sbiz.or.kr), 업종·시장 통계는
KOSIS 국가통계포털, 임대료·설비 비용은 실제 견적서 2~3곳 비교, 인허가는 관할 시·군·구청 담당 부서 문의.
섹션은 소제목(##, ###)으로 구조화하고, 비교·구성·수치 정리에 적합하면 마크다운 표를 사용하세요.
각 문단은 이 사업에만 해당하는 구체적 내용으로 쓰고, 다른 업종에 복붙해도 말이 되는 범용 문장은 실패로 간주합니다.
과장, 성공 보장, 가상 고객 인용, 존재하지 않는 경쟁사·URL을 금지합니다.
출력은 해당 섹션의 마크다운 본문만 작성하세요. 최상위 제목(#)이나 코드펜스는 넣지 마세요.
```

시스템 프롬프트에 **`[사업 정보]` + `[이 문서의 성격]` 블록**이 이어붙음.
25회 내내 동일하게 유지되어 **Anthropic prompt cache**가 걸리도록 설계됨(코드 주석에 명시).

**설정**

| 항목 | 값 |
|---|---|
| `maxOutputTokens` | 8000 (예전 4000 → 잘림 사고로 상향, 주석에 경위 기록) |
| `effort` | `medium` (OpenAI에만 적용, Claude는 무시) |
| `timeoutMs` | 180,000 (180초) |
| `cache` | `true` (Anthropic `cache_control: ephemeral`) |
| `temperature` | **미설정** |

### 4-2. 유형별 지침 블록

`lib/plan-builder/plan-type-guidance.ts` — `planTypeGuidanceBlock()`

7개 유형 각각에 `reader`(읽는 사람) / `decision`(내리려는 결정) / `tone` / `emphasize[]` / `avoid[]` 정의.

예시 — 정부지원 PSST:

```text
[이 문서의 성격 — 정부지원 · PSST 사업계획서]
읽는 사람: 예비창업패키지·초기창업패키지 등 정부지원사업 심사위원
그 사람이 내리려는 결정: 한정된 심사 시간 안에 이 팀에 지원금을 배정할지
문체: 심사 기준 어법. 항목마다 근거를 붙이고, 문제인식→실현가능성→성장전략→팀 순의 논리 사슬이 끊기지 않게 쓴다.
반드시 다룰 것:
- 문제인식: 이 문제가 얼마나 크고 왜 지금인지 — 창업 동기와 필요성
- 실현가능성: 아이디어를 실제로 만들 수 있다는 근거 — 개발·준비 현황과 차별성
- 성장전략: 자금을 받으면 무엇을 언제까지 달성하는지 — 자금 사용 계획과 성과 지표
- 팀 구성: 왜 이 사람(들)이 해낼 수 있는지 — 이력과 역할 분담
쓰지 말 것:
- 심사위원이 검증할 수 없는 수치 — 출처 없는 시장 규모, 근거 없는 점유율 목표
- 지원금과 무관한 장기 비전 서술로 지면을 채우는 것
```

7개 유형 전부 정의됨: 창업 초기 / 성장·확장 / 정부지원 PSST / 간단 / 내부용 / 창업 초기 재무 예측 / 정밀 재무 모델

## 9. 재무계획 생성 방식

### ✅ 이 시스템에서 가장 잘 구현된 부분 — LLM이 숫자를 만들지 않음

`lib/plan-builder/financials.ts` (505줄)의 **순수 산식 계산 엔진**

| 숫자 | 생성 방식 |
|---|---|
| 판매가격 | 사용자 입력 (`unit_price`) |
| 판매량 | 사용자 입력 (`monthly_volume`) + 성장률 복리 |
| 변동비 | 사용자 입력 (`variable_per_unit`) |
| 고정비 | 사용자 입력 (`fixed_total`) **+ 인건비(`staff_monthly`) 자동 합산** |
| 인건비 | 사용자 입력 |
| 광고비 | 🟡 `promo_budget`으로 묻지만 **손익 계산에 반영되지 않음** |
| 원가 | 변동비와 동일 개념 |
| 공헌이익 | `판매가 − 변동비` (계산) |
| 손익분기점 | `ceil(월고정비 ÷ 건당공헌이익)` (계산) |
| 12개월 매출 | `startingVolume × (1+growth)^(m−1) × unitPrice` (계산, 월별 루프) |
| 영업이익 | `공헌이익 − 고정비` (계산) |
| 흑자전환 시점 | 월별 영업손익 첫 양수 월 (계산) |
| 투자 회수 시점 | 누적 손익 ≥ 초기투자 월 (계산) |
| 3년 예측 | `projectYears()` — 같은 산식 36개월, **"정밀 재무 모델" 유형만** |
| 5년 예측 | 🔴 미구현 |
| 필요자금 | 🟡 구간 선택(`amount`)만, 계산 없음 |
| 자금조달계획 | 🟡 다중선택(`sources`)만, 금액 배분 계산 없음 |

**성장률 매핑** (`GROWTH_MAP`)

```ts
"완만한 성장 (월 5%)": 5,
"빠른 성장 (월 12%)": 12,
"계절 따라 등락 (연평균 월 6%)": 6,
"보수적으로 유지 (성장 0%)": 0,
```
주석: *"'천천히'가 실제로는 연 1.8배(월 5% 복리)라 초보 창업자가 라벨만 보고 과대 추정 문서를 만들던 것을 바로잡는다."*

**부가 기능**

- **한글 금액 파서** (`parseAmount`): `"1억5천만"` → 150,000,000 / `"150만원"` → 1,500,000 / `"49,000원"` → 49,000

- **재무 검토 화면** (`app/plan/FinancialReview.tsx`): 파싱 결과를 사용자가 확인·보정. 보정값은 `financials/__review` 가상 섹션에 저장되며 원문 파싱값보다 우선
- **단위 착오 경고**: `"1,000원 미만입니다. '만원'·'천원' 단위를 빠뜨리지 않았는지 확인해주세요."`

**정합성 검사 15종 (규칙 기반, AI 아님)**

1. 진행 단계와 시작 여부 불일치 (아이디어 단계인데 시작했다고 답변)
2. 시작 전인데 성과가 있다고 되어 있음
3. 상품 가격 ≠ 재무 판매가
4. 1건당 변동비가 두 곳에서 다름
5. **판매가 ≤ 변동비 → "팔수록 손해가 나는 구조입니다"**
6. 손익분기 건수 답변 ≠ 계산값
7. 손익분기 시점이 계산상 12개월 내 도달 불가
8. 손익분기 시점이 계산보다 낙관적
9. 인력을 쓰는데 인건비 0
10. 조직 규모와 실제 인력 불일치
11. 매출 이력이 서로 다름
12. 구독 상품인데 매출 방식에 구독 없음
13. 고객 채널 ∩ 홍보 채널 = ∅
14. 영업 범위가 두 곳에서 다름
15. 초기 투자 > 조달 계획 / 목표 기간 내 손익분기 도달 불가 / 상품·서비스 둘 다 없음

발견된 충돌은 **프롬프트에 주입**되어 AI가 한쪽을 골라 단정하지 않도록 지시됨

## 13. DB 구조

### 13-1. `plan_states` — 계정당 1행, 전체가 jsonb 하나

`supabase/migrations/0019_plan_states.sql`

```sql
create table if not exists public.plan_states (
  owner_hash text primary key,       -- FK 없음, guest identity 해시
  title text not null default '새 플랜',
  plan_type text not null default '창업 초기 · 사업계획서',
  data jsonb not null default '{}'::jsonb,  -- ★ 모든 플랜이 여기
  updated_at timestamptz not null default now()
);
alter table public.plan_states enable row level security;  -- policy 0개 = service-role 전용
```

`data` 구조 (`ServerPlanState`):

```ts
{
  business: { name, description, role, industry, region, stage },
  plans: [{
    id, title, planType, createdAt, updatedAt,
    sections: { "chapter/section": { markdown, html, generatedAt, edited?, locked?, previous? } },
    answers:  { "chapter/section": { questionId: value } },
    inheritedFrom?: { title, count }
  }],
  activePlanId
}
```

**제한**: plans 최대 30개 / id 60자 / title 120자 / description 1000자.
**sections·answers 자체에는 크기 제한 없음.**

**저장 방식**: 병합(merge) — 페이로드에 없는 서버 플랜은 삭제하지 않음. 같은 id면 `updatedAt` 최신이 승리.
Supabase 미설정 시 프로세스 메모리 Map 폴백(재시작하면 소실).

## 18. 현재 코드상 문제점

1. **⚠️ 시장 데이터 공백** — hallucination은 프롬프트로 강하게 막았으나(강점), 대신 **TAM/SAM/SOM·시장규모·성장률·경쟁사가 전부 "추가 정의 필요"로 남음**. 심사용 문서로서 결정적 약점.
2. **🔴 대표자 경력·팀 이력 질문 부재** — PSST 4대 항목 중 Team을 채울 입력이 없음.
3. **🔴 업종 차별화 없음** — 카페와 SaaS가 같은 138문항·같은 단가×수량 모델.
4. **⚠️ 재무모델 단순** — 상품 1종·단가 1개 전제. 복수 상품군, 계절성, 원가 변동, 광고비→매출 연동 없음. `promo_budget`은 묻고 계산에 반영 안 됨.
5. **🔴 검토 AI 없음** — 작성 1패스. 근거 부족·논리 비약을 AI가 검증하지 않음(규칙 15종만).
6. **⚠️ JSON schema 미사용** — `json_object`만 쓰고 사후 파싱. deck 생성은 잘림 때문에 2회 재시도 로직이 붙어 있음.
7. **⚠️ DB 단일 jsonb** — 계정당 1행에 전 플랜. 섹션 단위 조회·부분 업데이트 불가, 동시 편집 시 통째 덮어쓰기 위험(updatedAt 비교 병합으로 완화).
8. **⚠️ 버전 관리 부재** — 되돌리기 1회. 재생성으로 잃은 본문 복구 불가.
9. **⚠️ RLS policy 0개** — service-role 전용 설계. 앱 레이어 `owner_hash` 검증에 전적으로 의존.
10. **⚠️ 비용** — 플랜당 25회 × 8,000토큰. 프롬프트 캐시로 입력은 절감되나 출력은 그대로. 무료 6회(3문서×2섹션)가 순수 원가.
11. **🟡 "추가 정의 필요" 남발 위험** — 프롬프트가 "3회 초과 시 실패"로 억제하지만 **검증 코드는 없음**(자연어 지시뿐).
12. **🟡 정부지원 형식 불일치** — PSST가 챕터 재배치 수준. 사업비 집행계획·추진일정·가점·평가항목 전무.

## 가장 큰 문제점 TOP 10

1. **시장 데이터가 통째로 비어 있다** — 할루시네이션은 막았지만 대안(검색·DB)이 없어 "추가 정의 필요"만 남는다. 심사·투자용으로는 치명적.
2. **검토·평가 AI가 없다** — 작성 1패스. 논리 비약·근거 부족을 아무도 잡지 않는다.
3. **업종 차별화가 0이다** — 카페와 SaaS가 같은 질문·같은 재무모델.
4. **대표자·팀 이력 질문이 없다** — PSST 4대 항목 중 Team을 채울 재료 부재.
5. **PSST가 이름뿐** — 챕터 재배치 수준. 사업비 집행계획·추진일정·가점 없음.
6. **재무모델이 단일 상품 전제** — 상품군·계절성·광고비 연동 없음.
7. **버전 관리 부재** — 되돌리기 1회. 재생성으로 날린 본문 복구 불가.
8. **DB가 계정당 jsonb 1행** — 섹션 단위 조회·부분 갱신 불가, 확장성 없음.
9. **구조화 출력 미사용** — `json_object`만. deck는 잘림 때문에 재시도 로직으로 버티는 중.
10. **투자유치/IR·정책자금·대출 전용 유형 부재** — 문서 종류 확장이 막혀 있다.

## 현재 잘 구현되어 있어 유지해야 할 부분

1. **리얼리티 게이트 프롬프트** — "지어내지 마라 + 확인처를 알려줘라"는 이 도메인에서 드물게 옳은 설계. 확인처(상권정보시스템·KOSIS·견적서·시군구청)를 구체적으로 지정한 점이 특히 좋음.
2. **재무 계산 엔진** — LLM에 숫자를 맡기지 않고 산식으로 계산. 한글 금액 파서(`1억5천만`), 물리적 상한(무한성장 방지), 성장률 라벨에 수치 노출(`월 5%`)까지 실무 감각이 살아 있음.
3. **정합성 검사 15종** — "팔수록 손해가 나는 구조입니다" 같은 판정은 규칙 기반이라 정확하고, **충돌을 프롬프트에 주입해 AI가 단정하지 못하게 하는 설계**가 특히 우수.
4. **`source: ai | fallback | failed` 3분류** — 실패를 표로 대체해 '완료'로 표시하던 사고를 구조적으로 막음. 재생성 차감도 `ai`일 때만.
5. **프롬프트 캐시 설계** — 25회 중 24회 캐시 읽기가 되도록 system/user 경계를 나눈 것.
6. **질문 분기 무결성 검증** — 모듈 로드 시 고아 질문을 `throw`로 잡는 방어 코드.
7. **결제·쿼터 서버 판정** — 화면이 아니라 서버가 판정하고, 스트리밍 우회까지 차단.
8. **수제 PDF의 한글 처리** — 폰트 서브셋팅(4MB→수백KB), Cloudflare Workers 제약(`readFileSync` 부재)까지 고려한 구현.
