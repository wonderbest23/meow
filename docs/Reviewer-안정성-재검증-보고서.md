# Reviewer 안정성 + 보완 후 재지적 운영 재검증

> **제품 코드 변경 0.** §17 의 자동수정 조건 중 실제로 재현된 것이 없어 Reviewer 를 손대지 않았다.
> 추가한 것은 검증용 테스트 1개(`review-digest`)뿐이다.

---

## 한눈에

| 항목 | 결과 |
|---|---|
| Reviewer 호출 | **10회** |
| AI 정상 완료 | **10 / 10 (100%)** — 종합감사의 "3회 중 1회 실패" **재현 안 됨** |
| 응답시간 | 83 ~ 201초 (중앙값 ~115초) |
| 점수 편차(같은 입력) | **8 ~ 12점** |
| 핵심 issue family 재현율 | **3/3** (문서 A 기준 3개 family) |
| 보완 후 동일 issue 재발 | **없음** |
| "공식 시장 근거 없음" | 근거 1건 문서 **0/3** · 근거 0건 문서 **3/3** |
| False positive | 1건 의심(PARTIAL), 명백한 FP 0건 |

## 측정 환경

- 운영 `https://oneulstart.com`, 2026-08-23
- Reviewer 모델 `claude-sonnet-5`, `maxOutputTokens: 16_000`, `timeoutMs: 150_000`, 라우트 `maxDuration: 180`
- 운영 6회는 실제 `/api/plan/review` (READ-ONLY)
- 보완 전/후 4회는 임시 진단 라우트로 실행 — **저장된 답변을 그대로 두고 메모리에서만 덮어써** 실제 `reviewPlan` 을 호출했다. 사용자 데이터는 한 글자도 바뀌지 않았다. 검증 후 라우트는 삭제했다.

## 테스트 문서

계정에 본문이 있는 플랜은 셋뿐이고, 그중 검토 가능한 규모는 둘이었다.

| | 플랜 | 섹션 | 본문 | 근거 | 성격 |
|---|---|---:|---:|---:|---|
| **DOC-A** | `plan_msd8isur_4cin1` | 15 | 36,122자 | **1건** | 로컬 소매(무인 꽃집) |
| **DOC-B** | `plan_msdxlihq_79hov` | 18 | 32,684자 | **0건** | 같은 업종, 답변 구성이 다름 |

> **고지**: §2 는 성격이 다른 문서 3개를 권했지만, 오늘창업은 **사업 1개 + 플랜 여러 개** 구조라
> 계정의 사업 정보가 "1인 무인꽃집" 하나뿐이다. SaaS·클래스 맥락을 만들려면 사업 정보를 바꿔야 하는데
> 그건 사용자 실데이터다. 그래서 **같은 업종의 서로 다른 두 문서 + 답변 조건을 바꾼 통제 실행**으로 대체했다.
> 근거 유무(1건 vs 0건)라는 결정적 대조가 우연히 확보된 것이 이번 표본의 강점이다.

### 실패 원인

**없다.** 종합감사에서 관측된 1회 실패(129초, `score: -1`)는 이번 표본에서 재현되지 않았다.
당시는 시장조사·전체문서 생성 배치가 동시에 돌던 고부하 상황이었고, 이번에는 그런 부하가 없었다.

다만 실패가 **불가능**하다는 증거도 아니다(표본 10회).

## 응답시간

- 최소 83초 / 중앙값 약 115초 / **최대 201초**
- 201초(#8)는 **주의 신호**다. LLM 호출 상한이 150초인데 `reviewPlan` 전체가 201초 걸렸다.
  같은 입력의 #7 이 103초였으므로 모델 쪽 변동으로 보이고, 라우트 `maxDuration: 180` 을 넘겼는데도
  응답이 온 것은 Cloudflare 가 그 값을 강제하지 않았다는 뜻이다.
- 사용자 체감으로 **2~3분**은 길다. 다만 이번 지시는 timeout 조정을 금지했고 실패도 없었으므로 손대지 않았다.

## 입력 / 출력 토큰

운영 로그 실측 1건:

```
[llm] usage kind=plan-review model=claude-sonnet-5 in=36,863 out=6,900 cache_read=2,441
```

**출력 6,900 / 상한 16,000 — 잘림까지 여유가 충분하다.** 절단 대응(`salvageTruncatedJson`)이 동작한 흔적도 없다.

### 입력 블록별 크기 (§14)

"39k 가 크다"가 아니라 **어느 블록이 큰지**를 쟀다.

| 확정 문제(deterministic) | 120자 | 0.3% | 133자 | 0.3% |
| AI 추정 참고정보 | 81자 | 0.2% | 81자 | 0.2% |

**결론: 입력의 85% 안팎이 검토 대상 본문 자체다.** 중복 정보로 낭비되는 블록이 없다.

지시대로 압축은 구현하지 않았다.

## False Positive 재감사

| issue | 대조 결과 | 분류 |
|---|---|---|
| 운영자금 미확보 | 자금 3,000만원 전액이 설비(진열대·키오스크·인테리어)에 배정, 운영자금 항목 없음 — 사실 | **TRUE POSITIVE** |
| 자금 사용처 ↔ 자산 목록 불일치 | `use_of_funds` 는 인테리어 포함, 자산 목록은 CCTV — 실재하는 불일치 | **TRUE POSITIVE** |
| **"172만원 오기"** | 본문 "1개월차 흑자 **172만원**" vs 시스템 표 **1,700,000원**. 300×(25,000−11,000)−2,500,000 = **1,700,000** — 본문이 틀렸다 | **TRUE POSITIVE** (2만원 차이를 정확히 포착) |
| 사업주 인건비 미반영 | `has_staff_cost: "no"`, `owner_pay: "no"` — 실제로 인건비 0 | **TRUE POSITIVE** |
| 마케팅 실행 구체성 부족 | 채널 2개·예산 15만원은 있으나 목표 판매량과의 연결은 없음 | **PARTIAL** |
| 공식 시장 근거 없음 (DOC-B) | evidence 0건 — 사실 | **TRUE POSITIVE** |
| **정부지원 요건 인용 (DOC-B #3, critical/fact_safety)** | 본문은 "아직 지원 승인이나 대출 실행이 완료된 상태는 아니다", "심사·승인 절차를 거쳐야 하므로 실행 시점이 개업일과 일치한다는 보장이 없다"고 **명시**한다. 지어낸 요건·금리·한도는 없었다. 정책자금 1,500만원은 `amount 3,000` − `self_fund 1,500` 의 산술 | **PARTIAL — 근거 약함** |

**명백한 false positive 0건.** 다만 마지막 항목은 `critical/fact_safety` 라는 가장 무거운 등급이 붙었는데
문서가 이미 미확정임을 밝히고 있어 과했다. 1/3 실행에서만 나왔고 `problem` 원문을 확보하지 못해
FALSE POSITIVE 로 확정하지는 않는다 — **PARTIAL 로 기록하고 재관측 대상으로 남긴다.**

## MarketEvidence 1건 / 다건 비교

**깨끗한 대조가 확보됐다.**

| | DOC-A (근거 1건) | DOC-B (근거 0건) |
|---|---|---|
| "공식 시장 근거가 아직 붙어 있지 않습니다" | **0 / 3** | **3 / 3** |

HOTFIX 1 이전 종합감사에서 이 issue 는 **3회 실행 3회 모두** 나왔다. 근거가 붙은 문서에서는 완전히 사라졌고,
근거가 없는 문서에서는 여전히 정확히 나온다. `deterministic.ts` 의 `evidence.length === 0` 조건이 의도대로 동작한다.

**근거 값 오해도 없었다.** DOC-A 의 근거는 "서울특별시 사업체 종사자수 5,800,617명"인데,
3회 실행 어디에서도 이 숫자를 우리 잠재고객 수로 읽은 issue 가 나오지 않았다.

> **미완**: §8 이 요구한 **근거 5건 문서**의 Reviewer 3회는 하지 못했다.
> 근거 5건이 붙은 플랜(`plan_dev_analyze`)은 본문 섹션이 0개라 Reviewer 가 돌지 않는다(`no_sections`).
> 근거가 여러 건인 상태를 만들려면 DOC-B 에 시장조사를 실행해 사용자 프로젝트에 evidence 를 추가해야 하는데,
> §2 의 "운영 사용자 데이터를 변경하지 않는다"에 걸려 하지 않았다. **다건 케이스는 여전히 미검증이다.**

## 보완 전 / 후 — 인건비

**이번 검증에서 가장 중요한 결과다.**

### BEFORE (실제 저장 상태)

```
financials/staffing: { has_staff_cost: "no", owner_pay: "no" }
```

- DOC-A #2: `ai/warning/finance | 사업주 노동의 기회비용 미반영` ✓ 재현
- 마케팅 BEFORE 실행: `ai/warning/finance | 사업주 인건비·기회비용 미반영` ✓ 재현
- 자금 BEFORE 실행: `ai/warning/finance | 사업주 인건비(기회비용) 미반영` ✓ 재현

### AFTER (답변만 메모리에서 채움 — 저장하지 않음)

```
financials/staffing: { has_staff_cost: "yes", staff_monthly: "150만원", owner_pay: "yes", staff_type: ["대표자 급여"] }
```

| 실행 | 점수 | "인건비 미반영" 재발 | 대신 나온 지적 |
|---|---:|---|---|
| #7 | 58 | **없음** | `critical/finance` **인건비 반영 여부와 손익분기 수치가 서로 모순됩니다** |
| #8 | 46 | **없음** | `critical/finance` **핵심 재무지표가 계산된 재무와 불일치합니다** |

#7 의 근거 문장을 그대로 옮긴다.

> "본문은 '인건비 항목 자체가 존재하지 않습니다'라며 대표자 급여를 0원으로 전제하고 손익분기 179건,
> 12개월 영업손익 36,850,000원을 산출했습니다. 그러나 **확정 사실에는 대표자 급여 150만원(staff_monthly)이
> 포함되어 있고, [계산된 재무]의 손익분기는 286건**…"

검산: (고정비 250만 + 인건비 150만) ÷ 공헌이익 14,000원 = **285.7 → 286건**. 정확하다.

이 한 문장이 세 가지를 동시에 증명한다.

1. 새 답변이 Reviewer 의 **확정 사실 블록에 도달**했다.
2. **재무 엔진이 재계산**했다 — 손익분기 179건 → 286건. HOTFIX 2 에서 인건비 지적을
   예/아니오(`owner_pay`)가 아니라 **금액(`staff_monthly`)부터 묻게 바꾼 것이 실제로 숫자를 움직인다.**
3. Reviewer 는 "미반영"을 반복하지 않고 **답변과 본문의 불일치**를 지적했다 — 새 정보에 맞는 다른 수준의 지적이다.

topPriority 도 "대표자 급여 반영 여부를 확정하고 손익분기·영업손익 수치를 [계산된 재무] 기준으로
전 섹션에 통일하세요" — 즉 **본문 재생성이 필요하다**고 정확히 안내한다.

**§10 판정: PASS.**

```
promo_channels: ["지역 커뮤니티·맘카페", "인스타그램"], promo_budget: "월 15만원", has_promo_budget: "yes"
```

DOC-A 3회 실행 어디에도 이 deterministic issue 가 **나오지 않았다 (0/3).**

대신 "마케팅 실행 계획 섹션 누락"·"채널만 있고 실행 방식 없음"처럼 **한 단계 더 들어간 지적**으로 바뀌었다.
이것이 §10 이 허용한 "새로운 정보에 맞는 다른 수준의 지적"이다.

**판정: PASS.**

## 보완 전 / 후 — 자금조달

### BEFORE 를 만들지 못했다

```
funding/requirements: { sources: 제거, use_of_funds: 제거, gov_detail: 제거, gov_program: 제거 }
```

이 상태로 실행했는데 **"조달 계획 없음" 유형 issue 가 나오지 않았다.**
대신 원래도 나오던 "개점 후 운영자금 미확보"가 나왔다.

원인은 명확하다. **답변만 지워도 본문에는 조달 구조가 그대로 서술돼 있다.**

> "| 자기자금 | 1,500만원 | 50% |" / "| 소상공인 정책자금 | 1,500만원 | 50% |"

Reviewer 는 답변뿐 아니라 **본문도 보므로**, 본문이 조달 계획을 담고 있으면 "없다"고 하지 않는다.

**이것은 결함이 아니라 정확한 동작이다.** 다만 이번 방법(답변만 제거)으로는 이 조건의 BEFORE 를
만들 수 없다는 뜻이고, **§11-B 는 미검증으로 남는다.**

## §12 — 답변만으로 해결되는 것 / 본문 재생성이 필요한 것

이번 측정이 이 경계를 선명하게 보여줬다.

| 유형 | 예 | 답변 저장만으로 |
|---|---|---|
| **사실 자체가 없다** | "홍보 채널과 예산이 비어 있습니다"(deterministic) | **해결됨** — 답변을 보고 판정하므로 |
| **본문이 그 정보를 반영하지 않았다** | "본문은 인건비 0원을 전제로 손익분기 179건을 썼는데 확정 사실은 150만원" | **해결 안 됨** — 본문 재생성 필요 |

deterministic 검사는 답변·근거·재무를 보므로 저장 즉시 반응한다.
AI 검토는 **본문까지 대조**하므로, 답변만 바뀌고 본문이 그대로면 "불일치"를 새로 지적한다.

**이 동작은 옳다.** 사용자가 답만 하고 재생성을 안 하면 문서는 실제로 낡은 상태이고,
Reviewer 가 그걸 알려 주는 것이 맞다. UI 가 보완 후 "관련 내용 다시 작성"을 권하는 흐름과도 일치한다.

# 최종 질문 5개

## 1. 현재 Reviewer 를 유료 서비스의 핵심 기능으로 신뢰해도 되는가?

**예 — 단, "점수"가 아니라 "지적 목록"으로서.**

10/10 성공, FP 0건, 핵심 문제 3/3 재현, 그리고 본문과 계산값의 2만원 차이를 잡아내는 정확도.
이 정도면 사용자가 돈을 낸 대가로 받을 만한 검토다.

다만 표본이 10회이고 문서가 사실상 2종이다. "실패하지 않는다"가 아니라 **"이번 조건에서 실패가 재현되지 않았다"** 가 정확한 표현이다.

## 2. 점수 숫자를 UI 에서 유지해야 하는가?

**지금 크기로는 안 된다.**

같은 문서·같은 입력에서 64 → 75, 58 → 46 이 나온다. 사용자가 문서를 고치지 않았는데 점수가 12점 움직이면
그 숫자는 정보가 아니라 소음이다. 지금 UI 는 이 숫자를 가장 큰 글씨로 강조한다.

제안(이번 범위 아님): 숫자를 빼거나 크게 줄이고, **먼저 고칠 것 N / 보완 N / 다듬기 N** 카운트를 주인공으로 둔다.
이미 그 카운트는 구현돼 있고 issue 는 재현성이 검증됐다.

## 3. Reviewer 문제 내용 자체는 안정적인가?

**핵심은 안정적, 주변은 흔들린다.**

운영자금·자금 불일치·마케팅 구체성은 3/3 재현. 반면 심각도가 같은 문제에서 `critical` ↔ `improvement` 로 갈리고,
주변 issue 는 1/3 로만 나온다. **"매번 같은 목록"이 아니라 "매번 같은 핵심 + 다른 곁가지"** 로 이해해야 한다.

실무적으로는 문제없다 — 사용자는 topPriority 상위 3개를 보고, 그 3개가 재현되기 때문이다.

## 4. HOTFIX 2 보완루프가 실제 Reviewer 까지 닫힌 고리인가?

**예. 이번에 처음으로 끝까지 확인했다.**

인건비 답변 → 확정 사실 블록 도달 → 재무 엔진 재계산(손익분기 179 → 286건) → Reviewer 가 "미반영"을 반복하지 않고
"답변과 본문이 불일치"라는 다음 단계 문제를 제기 → topPriority 가 재생성을 안내.

특히 **HOTFIX 2 에서 인건비 지적을 예/아니오가 아니라 금액부터 묻게 바꾼 것**이 없었다면
숫자가 전혀 움직이지 않았을 것이다. 그 수정의 효과가 운영 Reviewer 응답으로 증명됐다.

한 가지 남았다 — 자금조달 갈래는 BEFORE 를 만들지 못해 미검증이다.

## 5. 지금 질문팩(subscription/commission/seat)을 추가해도 되는 단계인가?

**예. 안정화 측면에서는 막을 이유가 없다.**

HOTFIX 0(데이터 유실) · 1(시장근거) · 2(보완루프)가 모두 닫혔고, 이번 검증에서 새 결함이 재현되지 않았다.
종합감사가 "새 기능 말고 안정화"라고 답했던 근거 — 시장근거가 한 번도 작동한 적 없음, 보완의 53% 가 값을 못 흘림,
Reviewer 33% 실패 — 는 **셋 다 해소되거나 재현되지 않았다.**

다만 팩을 추가하기 전에 두 가지를 먼저 정리하는 편이 낫다.

1. **점수 표시** — 코드 변경 없이 UI 만으로 가능하고, 신뢰도에 직접 영향을 준다.
2. **근거 5건 문서의 Reviewer** — 이번에 못 한 유일한 측정이다. 팩을 추가하면 사업 종류가 늘어
   근거 건수도 늘 텐데, 다건 상태를 한 번도 검증하지 못한 채로 넓히는 것은 순서가 뒤바뀐다.

이 둘은 각각 반나절 안쪽이다.
