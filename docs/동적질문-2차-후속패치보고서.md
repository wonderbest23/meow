## 1. 고친 버그

운영 실측에서 쇼핑몰 사업이 동적 질문에 **방문자 3,000명 · 전환율 2%를 confirmed 로 답했는데도**, `PlanBusinessContext` 에 해당 필드가 없어 Writer 에게 전달되지 않았고 본문이 이렇게 나왔다.

> (수정 전) "유입 경로(인스타그램 광고 등)와 실제 전환율은 **아직 사용자가 확인한 값이 아니므로**, 이번 섹션에서는 방문자 수·전환율 같은 수치를 임의로 제시하지 않는다."

환각은 아니지만 **사용자가 답한 것을 답하지 않았다고 쓴 사실 오류**였다.

commerce 필드 몇 개를 빌더에 하드코딩하지 않고, **팩이 선언하고 빌더는 실어 나르기만 하는 구조**로 고쳤다. SaaS churn·ARPU·좌석 회전율·GMV·수수료율이 나중에 추가돼도 빌더는 그대로다.

## 3. BusinessMetric 실제 타입

```ts
export type MetricCategory =
  | "revenue" | "capacity" | "conversion" | "traffic"
  | "cost" | "retention" | "operation" | "other";

export interface BusinessMetric {
  id: string;                                   // 팩 슬롯 id (화이트리스트)
  label: string;                                // "월 방문자 수(예상)"
  value: string;                                // 사용자가 답한 원문 "3,000명"
  unit?: string;                                // "명"
  status: "confirmed";                          // confirmed 외에는 타입상 존재할 수 없다
  source: "user_answer" | "calculation";        // ai_inference 는 타입에 없다
  category: MetricCategory;
}

interface PlanBusinessContext {
  …
  metrics: BusinessMetric[];
}
```

`status` 를 리터럴 `"confirmed"` 로, `source` 에서 `ai_inference` 를 **타입 차원에서 제외**했다. 추정값이 지표로 새는 경로가 컴파일 단계에서 막힌다.

## 4. PackSlot metadata

```ts
export interface PackSlot {
  …
  contextMetric?: { label: string; unit?: string; category: MetricCategory };
}
```

부착한 13개 슬롯:

| 팩 | 슬롯 | label | unit | category |
|---|---|---|---|---|
| class | `seatsPerClass` | 회당 정원 | 명 | capacity |
| class | `classesPerMonth` | 월 수업 횟수 | 회 | capacity |
| class | `occupancyRate` | 예상 평균 참석률 | % | capacity |
| class | `materialCost` | 1인당 재료비 | 원 | cost |
| class | `venueCost` | 월 공간 비용 | 원 | cost |
| commerce | `monthlyVisitors` | **월 방문자 수(예상)** | 명 | **traffic** |
| commerce | `conversionRate` | **구매 전환율(예상)** | % | **conversion** |
| commerce | `cogs` | 1건당 상품 원가+포장·배송 | 원 | cost |
| commerce | `adBudget` | 월 광고비 | 원 | cost |
| commerce | `fixedOps` | 월 고정비 | 원 | cost |
| unit_sale | `unitCost` | 1건당 원가 | 원 | cost |
| unit_sale | `fixedTotal` | 월 고정비 | 원 | cost |
| unit_sale | `initialInvestment` | 초기 투자 금액 | 원 | cost |

**의도적으로 붙이지 않은 것**: `classPrice`·`aov`·`unitPrice`·`monthlyVolume`. 이미 `revenue.unitPrice`·`revenue.volume` 로 나가므로 붙이면 같은 값이 프롬프트에 두 번 실린다. 실수로 붙이면 **모듈 로드 시 throw** 한다:

```ts
if (s.contextMetric && s.mapsTo && ALREADY_IN_CONTEXT.has(`${s.mapsTo.sectionKey}.${s.mapsTo.qid}`))
  throw new Error(`${pack.id}.${s.id} 은 이미 구조화 필드로 전달된다 — contextMetric 을 빼라`);
```

`(예상)` 접미사가 "목표값 vs 실적" 구분을 담당한다 — 실측에서 실제로 작동했다(§8).

## 5. 빌더 — 팩이 화이트리스트

```ts
for (const slot of slotsForPack(packForAnalysis(rec.analysis))) {
  const m = slot.contextMetric;
  if (!m) continue;                                  // 팩이 선언하지 않은 슬롯
  const answered = rec.slots[slot.id];
  if (!answered || answered.status !== "confirmed") continue;   // inferred·unknown 차단
  const value = (answered.value ?? "").trim();
  if (!value) continue;
  ctx.metrics.push({ …, status: "confirmed", source: "user_answer", category: m.category });
}
```

`slotsForPack()` 을 순회하므로 **AI 가 만든 임의 slot id 는 애초에 루프에 들어오지 않는다**. 팩마다 빌더를 고칠 일이 없다.

### 파생값 (source = "calculation")

```ts
const derived = pack.deriveVolume?.(numericSlots(rec.slots)) ?? null;
const savedVolume = parseAmount(get("financials/revenue", "monthly_volume"));
if (derived && savedVolume != null && savedVolume === derived.value) {
  ctx.metrics.push({ id: "derivedVolume", label: "월 판매량 산출 근거",
    value: derived.formula, status: "confirmed", source: "calculation", category: "capacity" });
}
```

사용자가 "숫자 확인" 화면에서 **그대로 승인했을 때만** 넣는다. 값을 고쳤다면 그 산식은 더 이상 그 숫자의 근거가 아니므로 넘기지 않는다 → "사용자가 확인하지 않은 파생값은 전달하지 않는다" 충족.

## 6. 섹션별 metric 전달 규칙

`Rule.metrics`(카테고리 목록) + `Rule.metricLimit`(기본 4). 선언이 없는 섹션은 지표를 아예 받지 않는다.

| 섹션 | 카테고리 | 상한 |
|---|---|---:|
| overview/summary | revenue · traffic · conversion · capacity · cost | **6** |
| market/products | revenue · capacity · cost | 4 |
| market/segments | traffic · conversion · capacity | 4 |
| market/personas | traffic · conversion | 4 |
| strategy/distribution | capacity · operation · traffic | 4 |
| strategy/price | revenue · cost · conversion | 4 |
| strategy/promotion | traffic · conversion · cost | 4 |
| strategy/people | capacity · operation | 4 |
| financials/revenue | revenue · traffic · conversion · capacity | **6** |
| financials/staffing | capacity · operation | 4 |
| financials/expenses | cost · operation | 4 |
| summary/executive | revenue · traffic · conversion · capacity · cost | **6** |
| **그 외 13개 섹션** | **(선언 없음 — 지표 전달 안 함)** | — |

카테고리 선언 순서대로 채우므로 상한에 걸리면 중요한 종류가 먼저 들어간다.

## 7. Writer 프롬프트에 추가된 블록

```
[사용자가 확인한 사업 핵심 지표]
- 월 방문자 수(예상): 3,000명
- 구매 전환율(예상): 2명 (2%)
- 월 판매량 산출 근거: 방문자 3,000명 × 구매율 2% = 약 60건 (계산값 — 사용자 확인함)
이 값들은 사용자가 직접 답했거나 확인한 값입니다. 새 숫자를 만들지 말고 필요한 경우 이 값만 사용하세요.
이름에 (예상)이 붙은 값은 사용자의 계획·추정치입니다. 이미 달성한 실적처럼 쓰지 마세요.
```

> "충돌 설명은 본문에서 한 문단 이내로만 다루세요. 어느 값이 어떻게 다른지에 대한 상세한 서술은 섹션 끝의 '추가 정의 필요 항목'으로 보내고, 본문이 충돌 설명으로 채워지지 않게 하세요."

## 8. 운영 재현 검증 — 실제로 고쳐졌다

배포 후 같은 쇼핑몰 데이터로 `/api/plan/generate` 3회 재실행(저장 없음, 전부 `200 / ai`).

**유실 문구(`사용자가 확인한 값이 아니` / `임의로 제시하지 않`)가 3개 섹션 전부에서 사라졌다.**

`overview/summary` — 표에 그대로 실렸고 "목표(예상)"으로 구분됐다:

| 월 방문자 수 | 3,000명 | 목표(예상) |
|---|---|---|
| 구매 전환율 | 2% | 목표(예상) |
| 월 판매량 | 약 60건 | 계산값(방문자×전환율) |

`market/segments` — 실적이 아님을 명시하며 사용:
> "월 방문자 3,000명, 구매전환율 2%, 월 판매량 약 60건은 사업자가 세운 **목표치이며 아직 달성한 실적이 아니다.** 첫 12개월 동안에는 이 목표치 대비 실제 방문자·전환율을 유입 채널별·연령대별로 나누어 추적하여, 어느 세그먼트에서 전환율이 2%를 상회하는지 … 확인할 계획이다."

`market/products`:
> "월 방문자 3,000명, 구매전환율 2%라는 수치는 사용자가 **계획 단계에서 세운 목표치**이며, 실제 트래픽을 발생시키기 전까지는 달성 여부를 알 수 없는 **예상값**이다."

→ `(예상)` 라벨이 의도대로 "목표/예상 vs 실적" 구분을 만들어냈다. 새로 지어낸 숫자는 없다.

## 11. 남은 것

- `retention`(SaaS 이탈률)·`operation` 카테고리는 타입에만 있고 아직 이를 쓰는 슬롯이 없다 — 해당 질문팩이 생기면 `contextMetric` 한 줄만 붙이면 된다.
- `strategy/people` 이 `derivedVolume`(capacity)을 받는데 인력 섹션에서의 활용도는 낮다. 실사용을 보고 카테고리를 조정할 여지가 있다.
- 이번 재현 검증은 쇼핑몰 1건·3섹션이다. class 팩의 정원·참석률이 실제 본문에서 어떻게 쓰이는지는 다음 회차 실측 대상.
